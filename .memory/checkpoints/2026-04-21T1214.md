## Architectural decisions worth carrying forward

- **Adapter-type breakage avoidance via `(adapter as any)` stopgap.**
  The `CommerceAdapter` type in `@commercejs/types` is consumed by
  every adapter (Salla, Medusa, etc.). Adding required methods
  would cascade-break. Stopgap used for the buyer reset methods:
  keep the legacy `forgotPassword`/`resetPassword` stubs on the
  interface, add the three new real methods on the concrete
  platform adapter only, consume via `(adapter as any)` at the
  storefront route boundary. Formalize when legacy stubs retire
  or when the next set of reset-style features arrives (T05
  email verification, T02's password reset for other tenant
  types). Pattern will recur.
- **Status triad discipline on any admin_users update.** The
  `invited` / `active` / `disabled` triad matters across auth
  flows. `completeAdminPasswordReset` landing without a
  `status='active'` flip was a real bug (caught in concurrent
  smoke, fixed as `834cfc5`). Any future flow that mutates
  `admin_users` needs to think about both `password_hash` AND
  `status`, not just the auth credential.
- **Enumeration hygiene vs timing side-channel.** The
  `/forgot-password` endpoints semantically return identical 200
  responses regardless of user existence. But timing is distinct
  — known-email 0.9s vs unknown-email 3s on cold deploy. Not
  exploited v1 (identical bodies + no cache-ability), but the
  future rate-limiter should equalize timing on the negative path.
- **Audit trail is free + load-bearing.** The
  `auth.password_reset_requested` row landing with
  `{email, expiresAt}` is the single best signal for "was the
  pipeline entered for a real match." Confirmed via the T13
  activity feed in this smoke. Same pattern for
  `auth.password_reset_completed`. Keep this hygiene for every
  future pre-auth flow (verify email, change email, etc.).
