## T02 scope (summary — full spec in tasks/T02.md)

Two password-reset flows on the merchant branch DB:

- **Admin reset** — `/admin/forgot-password` +
  `/admin/reset/[token]`; tokens in a new `password_resets` table
  with `actor_type='admin'`. Platform methods
  `admin.auth.{requestAdminPasswordReset, verifyAdminPasswordResetToken,
  completeAdminPasswordReset}`. Template
  `admin-password-reset.ts`. Route namespace `/api/admin/…`.
- **Buyer reset** — `/account/forgot-password` +
  `/account/reset/[token]`; same table with `actor_type='buyer'`.
  Platform methods via a buyer-auth domain (fill in the stubs
  currently at `packages/platform/src/domains/customers.ts:123`).
  Template `buyer-password-reset.ts`. Route namespace
  `/api/storefront/account/…`.

Shared decisions already locked in T02.md:

- Single `password_resets` table (not two). Discriminator column
  `actor_type ('admin' | 'buyer')`. Cleaner than two near-identical
  tables.
- 1-hour expiry (vs 7-day staff invite). Industry standard for
  reset links.
- Enumeration-safe `/forgot-password` — always returns 200
  regardless of user existence. Dispatches only if the user is
  real. Audit row lands on every request for ops visibility.
- Cross-actor-type rejection hardening in `verify*` methods so an
  admin reset token can't exchange into a buyer flow and vice
  versa.
- Auto-login on reset complete (matches T01 invite-accept UX).
- Token primitives identical to T01: 32 bytes → base64url → sha256
  at rest. Consider factoring `generateRawToken`/`hashToken` out of
  `admin/auth.ts` into a shared `database/tokens.ts` module — low-
  risk, saves future copy-paste.
