# T03: Products CRUD

---

**Status**: ✅ **Completed** (2026-04-17)
**Effort**: Large
**Blocked By**: T02 (admin shell must exist for nav + layout) ✅

## Goal

A logged-in merchant can list their products with pagination + search, create a new product,
edit an existing one, and delete a product. All operations call tenant-scoped
`event.context.admin.*Product*` methods. Product images are covered in T04 — this task
handles the rest of the product form.

## Context

`packages/platform/src/admin/products.ts` already implements the full CRUD:
`getProduct / createProduct / updateProduct / deleteProduct / listProducts` with proper
`CreateProductInput` / `UpdateProductInput` types (name/nameAr, sku, price/compareAtPrice,
categories, variants, attributes, tags, i18n fields). T03 is HTTP wrappers and Vue forms.

The form is the biggest surface area — products have 20+ fields plus nested variants and
attributes. v1 can defer variants (most MENA stores sell single-variant products) and ship the
simple case first.

## Requirements

### 1. API routes under `apps/dashboard/server/api/admin/products/`

- `index.get.ts` — `?page=&pageSize=&search=&sort=` → `admin.listProducts(params)`.
- `index.post.ts` — body is `CreateProductInput` → `admin.createProduct(body)`.
- `[id].get.ts` — `admin.getProduct(id)`.
- `[id].patch.ts` — body is `UpdateProductInput` → `admin.updateProduct(id, body)`.
- `[id].delete.ts` — `admin.deleteProduct(id)`.

Every handler starts with `const session = await requireMerchantSession(event)` (from T01).
Every handler reads from `event.context.admin`.

### 2. Request validation

Zod schemas for `CreateProductInput` / `UpdateProductInput`. Reject malformed input at the
route boundary with 400. Prefer aligning with existing validation patterns in
`apps/dashboard/server/api/storefront/*` — check one of those routes for the current Zod style
before choosing an approach.

### 3. List page (`/admin/products/index.vue`)

- Search input (debounced).
- Pagination controls.
- Status filter (draft / active / archived).
- Table: primary image thumbnail, name (en + ar if present), SKU, price, inventory, status, actions (edit / delete).
- "New Product" CTA → `/admin/products/new`.

Use `@nuxt/ui` v4 `UTable` with slot customisation for the image + actions column.

### 4. Create page (`/admin/products/new.vue`)

Form sections:

1. **Basics** — name (en, ar), description (rich text or textarea), SKU, status.
2. **Pricing** — price, compare-at price, currency (pre-filled from store), VAT rate, VAT included.
3. **Inventory** — in stock, inventory quantity, quantity limit, requires shipping.
4. **Categories** — multi-select of existing categories (simple `<USelectMenu>` multiple).
5. **Tags** — comma-separated input → `string[]`.
6. **Images** — deferred to T04.
7. **Variants** — DEFERRED to v2 unless trivial.
8. **Attributes** — small repeater: code / name / value.

Submit posts to `/api/admin/products`, navigates to `/admin/products/:id/edit` on success.

### 5. Edit page (`/admin/products/[id]/edit.vue`)

Same form as create, pre-filled from `admin.getProduct(id)`. Submit sends a `PATCH` with only
the changed fields (`UpdateProductInput = Partial<CreateProductInput>`).

Delete action on this page with a `UConfirm` / `UModal` — on confirm, DELETE the product, navigate
back to list.

### 6. Currency display

Every price rendered must use the store's currency (from `useStoreInfo`). Don't hard-code SAR —
the store settings are authoritative.

### 7. Integration points

- `event.context.admin.listProducts()` — already returns `PaginatedResult<Product>`.
- Category dropdown needs a list of existing categories. `admin.listCategories()` is NOT in
  the `AdminAPI` type today — we either add it (safe, it's just a listing) or inline a query in
  one of the route handlers. **Decide during implementation**; prefer adding to the admin
  domain if missing.

## Implementation Notes

- **Variants deferred**: single-variant products cover the MENA market's common case. Variants can land in a T-later. If a product has variants in the DB already, the edit form should display them read-only with a "Variants UI coming soon" note — don't let users accidentally delete variant data by editing a non-variant product.
- **Slug auto-generation**: `createProduct` auto-generates slugs from name. UI should not require a slug field for v1.
- **Status default**: `createProduct` defaults `status: 'draft'`. Surface a "Save as draft" vs "Save and publish" button pair on the create form.
- **Large catalogs**: `listProducts` is paginated, default pageSize probably 20. Confirm default and expose a page-size selector.
- **Image field**: form holds an `images: CreateProductImageInput[]` array that starts empty. T04 wires this up.

## Execution Summary

**Completed**: 2026-04-17

**What was implemented**:

API routes in `apps/dashboard/server/api/admin/`:
- `products/index.get.ts` — paginated list (`?page=&perPage=&search=&status=&sortField=&sortDirection=`), Zod-validated via `listProductsQuerySchema`.
- `products/index.post.ts` — create product, Zod-validated via `createProductSchema`.
- `products/[id].get.ts` — fetch single product, 404 on miss.
- `products/[id].patch.ts` — update via `updateProductSchema` (= `createProductSchema.partial()`).
- `products/[id].delete.ts` — delete product.
- `categories.get.ts` — flat listing for the form's multi-select.

All six routes open with `await requireMerchantSession(event)` (T01's guard) and read from `event.context.admin`. Body/query validation goes through a new `parseOrThrow(schema, value)` helper in `server/utils/admin-validate.ts` that emits a 400 with `path: message` from the first Zod issue. Schemas live in `server/utils/admin-schemas.ts`; they re-declare the `CreateProductInput` shape since `@commercejs/platform` types can't be introspected at runtime.

Platform changes (`packages/platform/src/admin/`):
- Added `listCategories()` to the categories domain + exposed it on `AdminAPI` (`types.ts` + `index.ts`).
- Added a `status` filter to `admin.listProducts()` via a new `AdminListProductsParams extends AdminListParams`.
- Added `status` to `findAllProducts()` in both Prisma (`admin-catalog.ts`) and Drizzle (`admin-catalog.ts` via `adminListProducts`) — parity-preserved.

Type changes (`packages/types/src/product.ts`):
- Added optional `status?: Maybe<'draft' | 'active' | 'archived'>` and `inventoryQuantity?: Maybe<number>` to `Product`. Adapters that don't expose these leave them undefined. `mapProduct` in `admin/products.ts` populates them from the row.

Storefront pages in `apps/storefront/app/`:
- `pages/admin/products/index.vue` — replaces the T02 stub. Debounced search (300ms), status filter, server pagination (`UPagination`), `UTable` with thumbnail / name (EN + AR) / SKU / formatted price / inventory / status badge / edit+delete row actions. "New product" CTA, empty state with CTA, delete confirm modal.
- `pages/admin/products/new.vue` — fetches categories + currency, renders `AdminProductForm`, POSTs on submit, redirects to edit page.
- `pages/admin/products/[id]/edit.vue` — `useFetch` product + categories, PATCHes on submit, confirm-modal delete → navigate back to list.
- `components/AdminProductForm.vue` — shared form: basics (EN + AR name/description, SKU, status), pricing (price, compareAt, VAT rate, VAT included), inventory (in-stock toggle, quantity, quantity limit, requires-shipping toggle), organization (categories `USelectMenu`, tags comma-input), attributes (repeater). Variants render read-only if present ("editor coming soon" alert) so edit-doesn't-nuke. Images deferred to T04.
- `composables/useAdminProductForm.ts` — `toPayload()` converts form value to the `CreateProductInput` / `UpdateProductInput` API shape; publish flag overrides status on create, preserves on edit.

Dependency: added `zod ^4.3.6` to `apps/dashboard/package.json`.

**Challenges encountered**:

- **Product type didn't expose `status`.** The unified `Product` type was buyer-facing — no publish status surfaced. Added `status` + `inventoryQuantity` as optional (`?:`) fields so admin lists could render status badges without changing adapters (Salla/Medusa leave them undefined). Non-breaking.
- **Drizzle/Prisma parity.** `admin.listProducts()` gained a `status` filter; added the same clause to both `adminListProducts` (Drizzle) and `findAllProducts` (Prisma) to keep `check-query-parity.sh` green if/when fly/eaas ever merges back to main.
- **Zod in dashboard.** Existing dashboard routes use hand-rolled type guards, not Zod — but T03 called for Zod at the route boundary. Added zod as a dashboard dep (it's already in `@commercejs/nuxt`). Keeping body/query parsing centralized in `admin-schemas.ts` means future admin CRUD (categories, staff, settings) can follow the same shape.
- **Chunk names.** Nitro's build output names the `products/index.get.ts` chunk as `api/admin/index.get.mjs` (collapses the `index` folder segment) — looks like a name collision but the route registration in `nitro.mjs` correctly binds `/api/admin/products` (GET + POST) and `/api/admin/products/:id` (GET/PATCH/DELETE). Verified by grepping the generated `nitro.mjs` route table.
- **Typecheck noise.** `pnpm --filter @commercejs/dashboard typecheck` still surfaces the pre-existing `Cannot find module 'h3'` + ioredis version-skew errors in `merchant-session.ts` / `queue.ts` / `session.ts` / `storefrontHandler.ts` / `tenant.ts` / `worker.ts` — same as at T02 shipping time. New T03 files inherit the same h3-module-resolution issue (matches T02's `stats.get.ts`); nuxt build still passes cleanly. Not a T03 regression.
