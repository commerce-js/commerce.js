# T05: Orders List + Detail (Read-First)

---

**Status**: ✅ **Completed** (2026-04-17)
**Effort**: Medium
**Blocked By**: T02 (admin shell must exist). Independent of T03 / T04.

## Goal

A logged-in merchant can view their orders — paginated list with status filter, search, and a
detail page with items, customer, shipping, and basic actions (mark as fulfilled with tracking,
issue refund with note). No order creation / editing from the admin side in this pass — orders
originate from the storefront checkout.

## Context

`packages/platform/src/admin/orders.ts` already implements `listOrders`, `getOrder`,
`fulfillOrder`, `refundOrder`. COD orders from `smoke.commercejs.cloud` are sitting in the
merchant's DB right now (browser smoke test placed one). T05 surfaces them.

Two important design constraints:

1. **Read-first**: list + detail + two action buttons. No editing order contents, no adding/removing line items. That's a v-later concern and usually wrong to do anyway (orders are historical).
2. **Payment/delivery actions are SEPARATE from order actions**: fulfillment only marks the order status + stores tracking info. Delivery dispatch (Armada/Parcel) is a distinct flow — do NOT wire it in T05. Just the `admin.fulfillOrder` call.

## Requirements

### 1. API routes under `apps/dashboard/server/api/admin/orders/`

- `index.get.ts` — `?status=&customerId=&dateFrom=&dateTo=&search=&page=&pageSize=` → `admin.listOrders(params)`.
- `[id].get.ts` — `admin.getOrder(id)`.
- `[id]/fulfill.post.ts` — body `{ trackingNumber?, trackingUrl?, note? }` → `admin.fulfillOrder(id, body)`.
- `[id]/refund.post.ts` — body `{ note?: string }` → `admin.refundOrder(id, note)`.

All gated by `requireMerchantSession`.

### 2. List page (`/admin/orders/index.vue`)

- Filter bar: status dropdown (pending / paid / fulfilled / refunded / cancelled), date range, search (order number or customer email).
- Table: order number, placed-at, customer email, total (in store currency), status chip, actions column ("View").
- Pagination.
- Click row / View → `/admin/orders/:id`.

### 3. Detail page (`/admin/orders/[id].vue`)

Top-level panels:

- **Order** — number, date, total, status, payment method (COD, card, etc.), tap charge ID if applicable.
- **Items** — SKU, name, qty, unit price, line total, image thumbnail.
- **Customer** — email, phone, account link if registered.
- **Shipping** — address, delivery method, tracking info (if set).
- **Billing** — address, tax breakdown (VAT).
- **Actions** — Mark Fulfilled (modal for tracking #/URL/note), Refund (modal for note). Disabled when status doesn't allow (e.g. can't fulfill an already-fulfilled order; can't refund a pending one).
- **History** — timeline of status changes (if the platform records these — check `admin.getOrder` return shape).

### 4. Currency + i18n

Every money value uses store currency via `useStoreInfo` — same helper as T03. Customer data
may include Arabic names — ensure the table doesn't break RTL layout for mixed-language rows.

## Implementation Notes

- **No order creation**: admin can't create orders. Orders come from the storefront checkout. If a merchant needs to enter a phoned-in order manually, that's a "Manual Order" v-later feature.
- **No partial fulfillment**: `fulfillOrder` is all-or-nothing in the platform API. Partial fulfillment (line-level) is a v-later enhancement.
- **No partial refund**: `refundOrder` takes a single note — there's no amount field in the current API. If merchants need partial refunds, the platform domain needs a schema change + API extension; flag as blocker, don't invent.
- **Audit trail**: verify during implementation whether the platform stores a status transition history that we can display in the "History" panel. If not, skip that panel — don't add it as a scope creep item here.
- **Export**: CSV export is a common merchant ask. Defer to a follow-up task.
- **Bulk actions**: no bulk mark-fulfilled in v1 — scope creep risk.

## Execution Summary

**Completed**: 2026-04-17

**What was implemented**:

- **API routes** (`apps/dashboard/server/api/admin/orders/`):
  - `index.get.ts` — Zod-parsed query (`status`, `customerId`, `dateFrom`, `dateTo`, `search`, `page`, `perPage`) → `admin.listOrders()`.
  - `[id].get.ts` — `admin.getOrder(id)`, 404 on not-found.
  - `[id]/fulfill.post.ts` — body `{ trackingNumber?, trackingUrl?, note? }` → `admin.fulfillOrder(id, body)`. 404 if the platform throws "Order not found", 400 otherwise.
  - `[id]/refund.post.ts` — body `{ note? }` → `admin.refundOrder(id, note)`.
  - All four gated by `requireMerchantSession` (session ↔ tenant check).
- **Zod schemas** (`apps/dashboard/server/utils/admin-schemas.ts`):
  - `listOrdersQuerySchema` with `orderStatusEnum = pending | processing | shipped | delivered | cancelled | refunded | returned`.
  - `fulfillOrderSchema` (trackingNumber, trackingUrl `url()`, note).
  - `refundOrderSchema` (note only).
- **List page** (`apps/storefront/app/pages/admin/orders/index.vue`): UTable with order#, placed-at, customer label, total, status chip, "View" action. Filter bar = 300 ms-debounced search + status dropdown + date-from + date-to. URL query state sync'd. Empty state. Pagination.
- **Detail page** (`apps/storefront/app/pages/admin/orders/[id].vue`): six panels — Actions (fulfill + refund with disabled-states), Items (image/name/qty/unit/line total), Order summary (number/status/payment method/totals breakdown), Customer, Shipping (RTL-safe address + method + tracking), Billing. Two modals: Mark Fulfilled (tracking# / URL / note) and Refund (note).
- **Status chip map** (actual platform enum): pending→neutral, processing→info, shipped→success, delivered→success, refunded→warning, cancelled→error, returned→error.
- **Action gating** (client UX; server re-enforces): Fulfill enabled for pending/processing; Refund enabled for processing/shipped/delivered. Unfulfillable / unrefundable states show a muted helper note.

**Challenges encountered**:

- **Gate: no history on AdminAPI.** `admin.getOrder` returns `Order` with no audit trail. The platform *does* record status transitions via `createOrderHistory` and expose `getOrderHistory()` at the domain layer, but it's deliberately absent from `AdminAPI`. Per the task's gate rule, History panel was SKIPPED rather than extending the platform API in this task.
- **Status enum mismatch with the spec.** The T05 stub referenced chip values `paid` / `fulfilled` that don't exist in `OrderStatus`. The platform enum is `pending | processing | shipped | delivered | cancelled | refunded | returned`, and `fulfillOrder` writes `status='shipped'` (the "fulfilled" state). UI renders the real enum; the modal copy says "Mark fulfilled" but the status transitions to `shipped`. No API extension.
- **Address shape is not a typed `Address`.** `shippingAddress` / `billingAddress` come back as `parseJsonField(row.shippingAddress)` — whatever the checkout stored. The detail page treats them as `any` with tolerant renderers: first/last name, two street lines, district/city/state/postalCode/country, Saudi `nationalAddress` if present. Missing pieces degrade gracefully.
- **No partial refund / partial fulfillment.** The platform API is all-or-nothing for both. Flagged as v-later schema change; NOT extended in T05.
- **Pre-existing typecheck noise.** `pnpm --filter dashboard typecheck` reports the same `Cannot find module 'h3'` / `event: any` errors on every `/api/admin/*` file, including T01–T04 routes. Build is green — `nitro` emits all four new chunks (`orders/_id_.get.mjs`, `orders/_id/fulfill.post.mjs`, `orders/_id/refund.post.mjs`, plus the list route merged into the shared `admin/index.get2.mjs`). Typecheck fix is a tooling concern, not a T05 regression.
- **Deploy not run.** Per the session's autonomous-rules, `fly deploy` is gated on explicit "go".
