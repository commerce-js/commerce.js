**Status**: 🟢 **In Progress**
**Effort**: Small — ~8–12 files. No new token table, no pre-auth pages, no Zod schemas. Template + 2 trigger sites + hosted-checkout dep bump.
**Blocked By**: None. T01 (2026-04-21) proved the SMTP pipeline end-to-end and T02 (2026-04-21) added the adapter-as-any stopgap that this task doesn't need to re-use. Both infrastructure pieces are already live on `commercejs-cloud.fly.dev`.

## Goal

Send an order-confirmation email to the buyer whenever an order becomes "real" — either placed directly (COD / bank transfer / free) through the storefront's native finalize path, or captured via the Tap card flow through hosted-checkout. One template, two trigger sites, idempotent.

## Context

Two distinct order-creation flows on `fly/eaas`, both ending with the buyer expecting confirmation:

1. **Storefront-native finalize (COD / bank / free)** — `apps/storefront/app/pages/checkout.vue` → `POST /api/storefront/checkout/complete` (dashboard) → `adapter.placeOrder(cartId)` → order row persisted directly in final status. This is the path for any payment method that doesn't need an external redirect.
2. **Hosted-checkout Tap flow (card)** — `apps/storefront/app/pages/checkout.vue` → external redirect to `https://checkout.commercejs.cloud/pay/cart` → `cart-pay.post.ts` creates order in `pending` status + opens Tap session → 3DS → `cart-confirm.get.ts` (synchronous redirect back) marks `processing` + Tap webhook (`webhooks/tap-payment.post.ts`) also marks `processing` (idempotent).

The confirmation email fires on the transition to a paid/processing state. For flow 1 that's the single `complete.post.ts` call. For flow 2 that's the Tap webhook — the authoritative, idempotent signal. We deliberately skip `cart-confirm.get.ts` and `cart-pay.post.ts` direct-capture branches to avoid race-condition duplicate sends; the webhook arrives within ~1–2s and the existing `if (order.status === 'processing') return 'already_processed'` guard already ensures exactly-once semantics.

Pipeline:

```
Storefront COD:
  POST /api/storefront/checkout/complete
    → adapter.placeOrder(cartId)
    → order.customer.email? → enqueue send-email(order-confirmation)
    → 200 order

Hosted-checkout card:
  cart-pay.post.ts creates order (pending)
    → user 3DS → cart-confirm.get.ts redirect → status → processing
    → Tap webhook arrives (or arrives first) → status transition branch
        → enqueue send-email(order-confirmation)
    → the other path's status update hits the idempotency branch → no-op
```

## Requirements

### 1. Email template

`apps/dashboard/server/emails/order-confirmation.ts`:

Vars:

- `orderNumber: string` — buyer-facing order number (not the UUID id)
- `buyerName?: string | null` — defaults to "Hi, there" greeting
- `storeName: string` — merchant display name (from `merchant.name`)
- `orderStatusUrl: string` — link back to the merchant's storefront `/order-confirmation?orderId={id}` (or `/account/orders/{id}` — use whichever the storefront exposes today, see Implementation Notes)
- `currency: string` — ISO 4217, for the subject line
- `totalFormatted: string` — pre-rendered total string (consume `order.totals.total.formatted`)
- `items: Array<{name: string, quantity: number, totalFormatted: string, imageUrl?: string | null}>` — one row per line item; `name` pre-resolved from `LocalizedString.en`; `imageUrl` nullable
- `shippingAddress?: {firstName: string, lastName: string, street: string, street2?: string | null, city: string, state?: string | null, postalCode?: string | null, country: string} | null` — null for digital-only orders
- `subtotalFormatted`, `shippingFormatted?`, `taxFormatted?` — sub-totals for the order summary block; each is pre-rendered. Shipping/tax may be null (free shipping, tax-included pricing).

Shape: subject + html + text + HTML-escaped vars (matches T01/T02 pattern). HTML includes a line-item table with product thumbnails (`<img src="{imageUrl}" />` skipped when null), subtotals block, shipping address block, and an "Order Status" CTA. Text version skips images. English only for v1; Arabic localization is a v2 concern — same TODO shape as the other templates.

Register in `_render.ts` alongside `staff-invite`, `admin-password-reset`, `buyer-password-reset`.

### 2. Storefront-native trigger

`apps/dashboard/server/api/storefront/checkout/complete.post.ts`:

After `adapter.placeOrder(cartId)` succeeds:

- Load the profile if `order.customerId` is present (for buyer name). If `customer.email` isn't on the order directly (Order type doesn't carry it — see Implementation Notes), look up via `admin.getOrder(order.id)` with customer join, OR pull from `getBuyerSession()` which carries the logged-in buyer's email.
- Skip if no email (guest checkout with no contact — valid state). Log "skipped — no email" and continue.
- Build `orderStatusUrl` from `getRequestHost(event, {xForwardedHost: true})` + `getRequestProtocol(...)` — same pattern as the staff-invite `inviteUrl`.
- `enqueueMerchantJob({type: 'send-email', data: {merchantId: merchant.id, to: email, template: 'order-confirmation', vars: {...}}})`.

## Implementation Notes

- **Order shape doesn't carry customer email directly.** `Order` type has `customerId: Maybe<Id>` but not email. Three options for the storefront-native path:
  1. Read email from `getBuyerSession(event)` — works when buyer is logged in.
  2. Load the customer via `admin.getCustomer(order.customerId)` — works for any customer-bound order.
  3. Skip if neither is available (guest with no email provided upfront — a valid state).
  Plan to do 1 → 2 → skip in that order. Never throw — missing email is a normal business state.

- **Order status URL on storefront.** `/order-confirmation?orderId=X` is the post-checkout URL today (used by `handlePlaceOrder` in `checkout.vue`). For the email CTA, use the same URL — buyers can bookmark it or revisit post-login. Alternatively `/account/orders/:id` if that page exists; verify during implementation.

- **Currency formatting.** Never hand-roll `amount.toFixed(2)` — `Price.formatted` is the source of truth, adapter-mapped. Templates consume `price.formatted` verbatim.

- **LocalizedString resolution.** `OrderItem.name` is `LocalizedString { ar, en, ... }`. Pick `en` for v1 since templates are English-only. When merchant locale drives email language (v2), pick `vars[merchant.locale] ?? vars.en`.

- **Race avoidance for Tap path.** Not attempting to fire from both `cart-confirm.get.ts` AND webhook — the webhook is authoritative and its existing idempotency guard naturally deduplicates. The downside: if the webhook is delayed or lost, no email. Mitigation: BullMQ's 5-retry exponential-backoff covers transient SMTP; Tap's webhook retries cover delivery. In practice Tap webhooks are reliable in minutes. Documented as an open risk in the Execution Summary post-acceptance.

- **`merchantId` in Tap webhook context.** Currently the webhook pulls `orderId` from `reference.order` and `cartId` from `metadata.cartId`. Add `merchantId` to `metadata` in `cart-pay.post.ts` so the webhook can look up the store name + enqueue to the right merchant-jobs queue with the right context. The queue itself is singleton (same Redis, same queue name), but `merchantId` is a required field on `SendEmailJob`.

- **Storefront routing for email links.** `getRequestHost(event, {xForwardedHost: true})` + `getRequestProtocol(event)` produces `{subdomain}.commercejs.cloud` or the custom domain — matches T01's pattern for `inviteUrl`. Works behind Fly's proxy without manual string-building.

- **Hosted-checkout enqueue mirror.** Only the producer side needs BullMQ deps; the worker stays in dashboard as the sole consumer. The mirror `queue.ts` is ~30 lines and only exports `enqueueMerchantJob` + `getMerchantQueue` + `closeMerchantQueue` — no worker-side imports.
