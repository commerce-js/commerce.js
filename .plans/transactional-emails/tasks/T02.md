## Goal

Ship password-reset for two distinct actor types that both live on
the merchant branch DB but sign in through different surfaces:

- **Admin (merchant staff)** — existing `admin_users` table;
  password-reset route at `/admin/forgot-password` posts to
  `/api/admin/forgot-password`, reset completion at `/admin/reset/
  [token]`.
- **Buyer (storefront customer)** — existing `customers` table
  (local-password auth, `password_hash` already on the model);
  `/account/forgot-password` + `/account/reset/[token]`.

Both flows use the same "token in URL, hashed at rest, single-use,
short expiry" pattern T01 proved for `staff_invites`. The template
system and SMTP dispatch require no changes — just two new template
files registered in `_render.ts`.

## Context

T01 shipped the infrastructure: `enqueueMerchantJob({type:
'send-email', ...})` → BullMQ → worker renders + dispatches. T02
adds:

1. One new merchant-branch table (`password_resets`) that carries
   both admin and buyer tokens — discriminated by an `actor_type`
   column — OR two separate tables (`admin_password_resets` /
   `buyer_password_resets`). Decision pending in Requirements §1.
2. Platform domain methods for request + verify + complete on each
   actor type.
3. Two templates: `admin-password-reset.ts` + `buyer-password-
   reset.ts`.
4. Four PUBLIC routes: request / verify / complete × 2 actor types
   (with `verify` collapsed into the storefront page load path so
   the user sees an "invalid link" page before typing a new
   password into a form that'll be rejected).
5. Four storefront pages: forgot-password / reset × 2 actor types.
6. Email enumeration hygiene: password-reset requests must NOT
   reveal whether the email exists. `POST /forgot-password` always
   returns `{ok: true}` regardless, and dispatches the email only
   when the row is found.

Pipeline (admin; buyer mirrors):

```
User POSTs /api/admin/forgot-password { email }
  → if admin_users row exists → createPasswordResetToken(userId)
                               → enqueue send-email(admin-password-reset)
  → always return {ok: true}   (no enumeration leak)

User opens /admin/reset/:token
  → storefront fetches GET /api/admin/reset/:token to validate
  → renders password + confirm form OR "link invalid" message

User POSTs /api/admin/reset/:token/complete { password }
  → verify + mark used + update password_hash (bcrypt)
  → issue merchant session cookie (auto-login matches T01)
  → redirect to /admin
```

## Requirements

### 1. Token storage schema (decide: shared vs split)

**Option A — shared `password_resets` table** with `actor_type`
column discriminating 'admin' | 'buyer' and `actor_id` referencing
the appropriate row. Cleaner schema, one lazy-migrate, one query
path.

**Option B — two tables** `admin_password_resets` +
`buyer_password_resets`. Mirrors `staff_invites` shape; FK
constraint per actor; two migrations.

**Recommendation: Option A** — the columns are identical, the
actor-type discriminator is a simple TEXT column, and it keeps the
platform domain surface smaller (one query file, not two). Revisit
if a third actor type (e.g. platform-operator) joins later.

Columns:
- `id` UUID PK
- `actor_type` TEXT NOT NULL (`'admin'` | `'buyer'`)
- `actor_id` UUID NOT NULL (FK is per-actor-type; enforce in app,
  not at the DB level since a composite FK isn't possible without
  per-row CHECK)
- `token_hash` TEXT NOT NULL UNIQUE
- `email_snapshot` TEXT NOT NULL
- `expires_at` TIMESTAMPTZ NOT NULL
- `used_at` TIMESTAMPTZ NULL
- `created_at` TIMESTAMPTZ NOT NULL DEFAULT now()
- Index on `token_hash`, `actor_type + actor_id` (composite)

Expiry window: 1 hour. Shorter than staff-invite (7 days) because
reset flows are initiated by the actor themselves — they're active.

### 2. Platform admin API extensions

`packages/platform/src/admin/auth.ts`:

- `requestAdminPasswordReset(email): Promise<PasswordResetSecret | null>`
  — returns token + expiry when the row exists, null otherwise.
  Caller (dashboard route) swallows the null and always returns
  `{ok: true}`.
- `verifyAdminPasswordResetToken(token): Promise<{adminUserId, email, expiresAt} | null>`
- `completeAdminPasswordReset(token, newPassword): Promise<AdminUserSafe>`
  — verifies + marks used + hashes + updates admin_users.

### 3. Platform buyer API extensions

New module `packages/platform/src/buyer-auth/reset.ts` (or fold into
an existing customers domain). Mirror methods:

- `requestBuyerPasswordReset(email)`
- `verifyBuyerPasswordResetToken(token)`
- `completeBuyerPasswordReset(token, newPassword)`

Same token table, `actor_type='buyer'`, `customers.id` as actor_id,
updates `customers.password_hash`.

### 4. Email templates

- `apps/dashboard/server/emails/admin-password-reset.ts`
- `apps/dashboard/server/emails/buyer-password-reset.ts`

Both follow the staff-invite shape: key + subject + html + text.
HTML-escape every var. English only for v1. Register in
`_render.ts`.

### 5. Dashboard routes (admin)

- `POST /api/admin/forgot-password` — PUBLIC. Zod: `{email}`. Always
  returns 200 `{ok: true}`.
- `GET /api/admin/reset/[token]` — PUBLIC. Returns `{email,
  expiresAt}` or 404.
- `POST /api/admin/reset/[token]/complete` — PUBLIC. Zod: `{password:
  ≥8}`. On success issues merchant session cookie, returns the
  AdminUserSafe shape.

### 6. Dashboard routes (buyer / storefront)

- `POST /api/storefront/account/forgot-password` — PUBLIC, always 200.
- `GET /api/storefront/account/reset/[token]`
- `POST /api/storefront/account/reset/[token]/complete` — issues
  buyer session cookie.

Exact route namespace depends on existing buyer-session patterns
in the storefront server dir — confirm during implementation.

### 7. Storefront pages

- `/admin/forgot-password.vue` (layout: false, pre-auth)
- `/admin/reset/[token].vue` (layout: false, pre-auth)
- `/account/forgot-password.vue`
- `/account/reset/[token].vue`

Mirror the `/admin/invite/[token].vue` shape from T01: on-mount
token validation, form-or-error branch, auto-login on accept.

### 8. Audit log

Write `auth.password_reset_requested` + `auth.password_reset_
completed` rows to the activity log. Actor for the request is
null (pre-auth) with `actor_email = <requested email>`. Actor for
completion is the admin/buyer themselves (session was just
issued). This is a small but useful forensic trail for security-
adjacent flows.

### 9. Test coverage

- Platform unit tests for all six new methods (request, verify,
  complete × admin/buyer). Cover: missing email → no-op, happy-
  path token generation, verify valid / expired / used / invalid,
  complete happy / short-password / wrong-token / race.
- Dashboard template render tests for both new templates (subject
  + html + text + HTML-escape).
- Route tests are acceptance-only (live smoke on

## Implementation Notes

- **Session after reset**: issuing a fresh session cookie on
  completion is standard (matches T01's invite accept). It
  smooths the "I just reset, now I need to log in again" UX
  snag.
- **Re-requesting reset while one is active**: don't void prior
  tokens on a new request — just issue a new one. Both remain
  valid until expiry / use. The user may have two emails open;
  neither should dead-end.
- **Email template language**: mention the requesting IP / UA
  briefly ("You requested a password reset from <IP>") so a
  recipient who didn't request one sees useful context. Low
  priority for v1; defer if it complicates the template.
- **Auto-login vs "go log in" after reset**: T01 chose auto-
  login for invite; T02 keeps the same shape. A security-
  sensitive merchant could prefer "redirect to /admin/login"
  instead — easy to toggle via a per-merchant setting later.
- **Rate limiting**: deferred to a future task (same as T01's
  invite routes). Low-volume in v1; add when abuse emerges.

**Challenges encountered**:

- **Adapter-type breakage if buyer methods added to
  `@commercejs/types`.** The `CommerceAdapter` type in
  `@commercejs/types` is consumed by every adapter (Salla, Medusa,
  etc.), so adding three new required methods would break every
  downstream adapter. Stopgap: keep the legacy `forgotPassword` +
  `resetPassword` stubs on the interface, add the three new
  methods on the concrete platform adapter only, consume via
  `(adapter as any)` in the storefront routes. Formalize in a
  later typed-surface pass once legacy stubs are retired.
- **Invited-status edge case.** If an invited admin uses the
  forgot-password flow instead of their invite link, the
  reset-complete was leaving status='invited', which the login
  path doesn't allow. Caught during smoke, fixed inline as
  `834cfc5`. Documented this in the architectural decisions
  carry-over — any future flow that updates `admin_users` needs
  to think about the status triad, not just password_hash.
- **Timing-side-channel on enumeration.** Unknown-email
  forgot-password returned in ~3s (cold-start) while known-email
  returned in ~0.9s — visible delta in a single A/B comparison.
  Not exploited for enumeration v1 (the semantic response is
  identical), but flagged as a polish item for when a rate-limit
  layer lands: equalize with a small wait on the negative path.
