# T01: Provider wiring + staff invite (first vertical slice)

---

**Status**: 🟡 **Planned**
**Effort**: Medium/Large — 15–20 files across platform + dashboard +
storefront. Sub-planning discipline applies: if scope creeps past ~25
files, pause and re-scope into T01a/T01b.
**Blocked By**: None. Three operator-side pre-reqs: (1) SMTP service
chosen (SES SMTP / Mailgun SMTP / Postmark SMTP / Resend-SMTP endpoint
/ self-hosted Postfix); (2) SMTP credentials provisioned from the

## Goal

Exercise the full transactional-email pipeline end-to-end on the
smallest real flow (staff invite) — so every subsequent task (T02
password reset, T03 order confirm, etc.) only needs to add a template
+ a trigger point, never touch the infra again. Ships the T09 deferred
invite flow as a side effect.

## Context

Merchant-admin-followup T09 shipped local-password staff CRUD on
2026-04-20 and explicitly deferred the email-invite flow to this
workstream. The `admin_users.status` column already has `'invited'` in
its triad — untouched by T09, reserved for this task. The owner
currently creates a staff user by typing a password and sharing it
out-of-band (T09's `/admin/staff/new.vue` shows the password once in a
post-create banner); after T01, the owner instead enters the
invitee's email + name + role, and the new user receives an email
with a single-use link that lets them set their own password.

Pipeline to prove:

```
Owner POSTs /api/admin/staff
  → creates admin_user row with status='invited', password_hash=NULL
  → inserts staff_invites row with token_hash, expires_at
  → enqueues SendEmailJob{template: 'staff-invite', to, vars}
  → audit: staff.invited

Worker consumes
  → loads template apps/dashboard/server/emails/staff-invite.ts
  → renders {subject, html, text} with vars
  → dispatches via createSmtpProvider({host, port, auth, from}).send('email', ...)
  → nodemailer returns messageId → job complete
  → on transient SMTP error (4xx / socket timeout) → BullMQ retry with exponential backoff

Invitee opens GET /admin/invite/:token
  → lookup by sha256(token) → check expires_at
  → render "set your password" form with email+name prefilled

Invitee POSTs /api/admin/invite/:token/accept with {password}
  → validates token again → sets admin_user.password_hash + status='active'
  → marks staff_invites.used_at=now()
  → issues session cookie → redirect to /admin
  → audit: staff.invite_accepted
```

## Requirements

### 1. New `staff_invites` table (merchant branch DB)

Add to `packages/platform/src/database/prisma/schema/` (new file or
fold into existing admin-user schema). Drizzle sibling in
`packages/platform/src/database/drizzle/schema.ts`. Idempotent lazy-
migrate in `migratePrisma()` + `migrateDrizzle()` — same pattern T13
used for `activity_events`.

Columns:

- `id` — UUID, PK
- `admin_user_id` — FK to `admin_users.id`, cascade on delete
- `token_hash` — TEXT NOT NULL, UNIQUE (sha256 of the raw token)
- `email_snapshot` — TEXT NOT NULL (denormalized; if the admin_user
  row gets deleted or the email changes, the invite still shows what
  it was sent to)
- `expires_at` — TIMESTAMPTZ NOT NULL
- `used_at` — TIMESTAMPTZ NULL (null = still usable)
- `created_at` — TIMESTAMPTZ NOT NULL DEFAULT now()
- Index on `token_hash`
- Index on `admin_user_id`

Expiry window: 7 days from creation. Tunable via an env constant at
the platform boundary.

### 2. Platform admin API extensions

`packages/platform/src/admin/auth.ts`:

- `createAdmin({email, password?, name?, role?, sendInvite?: boolean})`
  — when `sendInvite: true`, allow `password` to be omitted; create
  row with `status='invited'`, `password_hash=NULL`. Returns the
  admin row AND a new `{inviteToken, expiresAt}` pair (raw token is
  returned once to the caller so the dispatcher can put it in the
  email; only the hash is stored). When `sendInvite: false` or
  unspecified, preserves current behavior.
- `createStaffInvite(adminUserId): Promise<{token, expiresAt}>` —
  generate token, hash, insert row. Separate export so token rotation
  is possible later.
- `verifyStaffInviteToken(token): Promise<{adminUserId, email} | null>`
  — lookup by sha256(token), check expires_at + used_at, return
  snapshot info or null.
- `acceptStaffInvite(token, newPassword): Promise<AdminUserSafe>` —
  validates (throws on expired/used), sets password_hash, flips
  status='active', marks invite used_at. Returns safe admin row.

All four methods: Prisma + Drizzle implementations, parity check green,
unit tests (at least: happy path accept, expired token, used token,
wrong token, createAdmin without password fails if sendInvite=false).

### 3. SMTP provider module (dashboard-local)

New file `apps/dashboard/server/utils/email-provider.ts`:

```ts
import { createSmtpProvider } from '@commercejs/notification-smtp'
import type { NotificationProvider } from '@commercejs/types'

let _provider: NotificationProvider | null = null

export function getEmailProvider(): NotificationProvider {
  if (_provider) return _provider
  const host = process.env.SMTP_HOST
  const port = Number.parseInt(process.env.SMTP_PORT ?? '587', 10)
  const user = process.env.SMTP_USER
  const pass = process.env.SMTP_PASS
  const from = process.env.SMTP_FROM
  if (!host) throw new Error('SMTP_HOST missing')
  if (!user || !pass) throw new Error('SMTP_USER / SMTP_PASS missing')
  if (!from) throw new Error('SMTP_FROM missing')
  _provider = createSmtpProvider({
    host,
    port,
    secure: port === 465,
    auth: { user, pass },
    from,
  })
  return _provider
}
```

Singleton. Lazy. Throws at call time (not import time) so tests /
worker boot in environments without the credentials still work.
Existing `SMTP_*` env-var names are preserved from the stub — no
secrets reshuffle.

### 5. Worker handler rewrite

Replace the stub in `apps/dashboard/worker.ts` `handleSendEmail`:

```ts
async function handleSendEmail(data: SendEmailJob['data']): Promise<void> {
  const rendered = renderEmail(data.template, data.vars ?? {})
  // data.subject overrides template.subject if provided (rarely needed)
  const subject = data.subject ?? rendered.subject
  const provider = getEmailProvider()
  const result = await provider.send('email', {
    to: data.to,
    subject,
    html: rendered.html,
    text: rendered.text,
    template: data.template,
  })
  if (!result.success) {
    throw new Error(`email ${data.template} → ${data.to} failed: ${result.error}`)
  }
  console.log('[worker] send-email OK merchant=%s to=%s template=%s messageId=%s',
    data.merchantId, data.to, data.template, result.messageId)
}
```

Throws on provider failure → BullMQ retries per queue default
(attempts: 5, backoff: exponential@5s).

- [ ] **Scenario 7 — Expired token.** Force-expire a fresh invite in

## Implementation Notes

- **Token format**: 32 random bytes, base64url-encoded → 43 chars. Not
  JWT (no state needed; the DB row IS the state). Stored as sha256
  hex (64 chars) in `token_hash`. Raw token exists only in the email
  URL; never logged, never stored.
- **Token-in-URL vs email-magic-link trade-off**: magic-link-only
  requires a cross-device flow. Token-in-URL is simpler and matches
  what GitHub / Shopify / Slack do for invites. Decision: token in URL.
- **Single-use enforcement**: check `used_at IS NULL` on lookup; set
  `used_at = now()` in the accept mutation with a `WHERE used_at IS
  NULL` predicate so a double-submit doesn't race (PG returns 0 rows
  affected → retry path returns 400).
- **Sender-identity string**: `SMTP_FROM` format is `"Display Name
  <local@domain>"`. Nodemailer parses this. Pick something merchant-
  friendly: `"CommerceJS Cloud <no-reply@commercejs.cloud>"`.
- **inviteUrl construction**: the invite goes to `/admin/invite/{token}`
  on the MERCHANT's storefront domain (e.g.
  `https://smoke.commercejs.cloud/admin/invite/...`), not the
  dashboard's `app.commercejs.cloud`. Because `/admin` is served from
  the storefront process on port `:3001`, not the dashboard `:3000`.
  Build the URL from `event.context.merchant.subdomain` or
  `customDomain` if set.
- **Email address for the `name` field**: the invite email prefills
  the admin_user's `name` from what the owner entered. If the
  invitee changes their name on the accept page, it overwrites the
  pre-set `name` — that's fine.
- **Password-hash null during invited state**: platform's
  `admin.auth.login` must reject `password_hash=NULL` rows (currently
  would call `bcrypt.compare(plaintext, null)` and crash). Add an
  early return: "Account pending invite". Worth a unit test.
- **Tenant context in the worker**: `handleSendEmail` does NOT need
  merchant DB access (templates are global; no per-tenant query).
  Skip the `runWithDb` wrapper — the job carries `merchantId` just
  for audit / routing purposes, not DB binding.
- **Storefront layout for /admin/invite**: the `admin` layout expects
  a session (sidebar would need a user context). Use the default
  (or minimal) layout for the pre-auth invite accept page.
- **Rate-limiting**: out of scope for v1. Callouts a TODO in the
  invite routes for a future task.
- **Deliverability**: the very first real email from a fresh DKIM-
  verified domain can land in spam until reputation builds. Not a
  code issue; document it in the acceptance checklist so we don't
  panic if scenario 2's inbox test takes a spam-check.
