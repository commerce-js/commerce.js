# T01: Storefront API routes in dashboard app

---

**Status**: ✅ **Completed** (code-complete; build green; live smoke test passed 2026-04-15)
**Effort**: Small
**Blocked By**: None — tenant middleware already populates `event.context.adapter`

## Goal

Add `/api/storefront/*` route handlers to `apps/dashboard` that expose the full commerce API
surface (catalog, cart, checkout, orders, customer auth) as tenant-aware endpoints, served at
`[subdomain].commercejs.cloud/api/storefront/*`.

## Context

This is Layer 2 of the three-layer model. The tenant middleware already resolves the merchant,
binds the Prisma client, and populates `event.context.adapter` on every request. These routes
are purely thin wrappers — they call `event.context.adapter.catalog.*`, `event.context.adapter.cart.*`,
etc. and return the result. No DB access needed in the route handlers themselves.

This is also the endpoint self-hosted storefronts call remotely (`apiRoutes: false` mode in
`@commercejs/nuxt`), so the route shape must exactly match what the module's composables expect.

The existing `packages/nuxt/src/runtime/server/api/_commerce/` routes are the reference —
they implement the same contract. The key difference here is that the adapter comes from
`event.context.adapter` (tenant middleware) rather than being initialized per-route from env vars.

## Requirements

All routes live under `apps/dashboard/server/api/storefront/`. Nitro maps this to
`/api/storefront/*`. The tenant middleware skip list must NOT include `/api/storefront` — these
routes require a resolved merchant.

### 2. Handler pattern

Every handler reads `event.context.adapter` (already bound by tenant middleware) and
calls the appropriate domain method. Example:

```ts
// server/api/storefront/products.get.ts
export default defineEventHandler(async (event) => {
  const { adapter } = event.context
  const query = getQuery(event)
  return adapter.catalog.getProducts({
    page: Number(query.page) || 1,
    limit: Number(query.limit) || 20,
    search: query.search as string | undefined,
    category: query.category as string | undefined,
  })
})
```

No try/catch needed in individual handlers — add a global error hook in `server/plugins/`
that formats adapter errors into h3 errors consistently.

### 3. Authentication for protected routes

Cart and checkout routes need a buyer session (not the merchant/admin session). Re-use Nitro's
`useSession` with a separate session name (`cjs-buyer-session`) so buyer cookies don't conflict
with the dashboard admin session (`cjs-dashboard-session`).

Orders and customer profile routes (`/auth/me`, `/orders`) also require buyer auth — return 401
if no buyer session.

### 4. CORS headers

Self-hosted storefronts that haven't set up a custom domain make cross-origin requests from
the browser side. Add CORS middleware that:
- Allows any origin in dev
- In production, allows: the request's `Origin` if it matches a verified `Domain` row for the
  resolved merchant, otherwise falls back to `[subdomain].commercejs.cloud`

```ts
// server/middleware/cors.ts
// Only applies to /api/storefront/* paths
```

### 5. Skip-list exclusion

Confirm `/api/storefront` is NOT in `SKIP_PREFIXES` in `server/middleware/tenant.ts`.
These routes must go through tenant resolution.

## Execution Summary

**Completed**: 2026-04-15 (code-complete + deployed + live smoke test passed)

**What was implemented**:

- 19 `/api/storefront/*` routes under [apps/dashboard/server/api/storefront/](apps/dashboard/server/api/storefront/) — thin wrappers over `event.context.adapter` (storefront reads, cart, checkout, auth) and `event.context.admin` (customer-scoped reads).
- [apps/dashboard/server/utils/buyerSession.ts](apps/dashboard/server/utils/buyerSession.ts) — sealed `cjs-buyer-session` cookie (30-day TTL) carrying `{ customerId?, cartId? }` separate from the dashboard operator session.
- [apps/dashboard/server/utils/storefrontHandler.ts](apps/dashboard/server/utils/storefrontHandler.ts) — `defineStorefrontHandler` wrapper that asserts tenant context (adapter + admin + merchant) before invoking the handler.
- [apps/dashboard/server/middleware/cors.ts](apps/dashboard/server/middleware/cors.ts) — CORS for `/api/storefront/*` only. Allows canonical subdomain + verified custom domains + dev origins. Resolves merchant itself (LRU-cached) because alphabetical middleware order puts CORS before tenant.
- [apps/dashboard/server/plugins/storefront-errors.ts](apps/dashboard/server/plugins/storefront-errors.ts) — Nitro error hook scoped to storefront paths; converts `CommerceError` to h3-shaped errors and logs unknown errors.

**Challenges encountered**:

- **Customer state is not request-scoped in `@commercejs/platform`.** The `customers` domain's `currentCustomerId` lives in a per-adapter-instance singleton, and the adapter is cached per-merchant in the tenant middleware. Two concurrent authenticated requests for the same merchant would stomp each other's customer state. Worked around by **not relying on `adapter.getCustomer()` / `adapter.getCustomerOrders()`** for protected routes — instead, `/auth/me`, `/orders`, and `/orders/:id` read the buyer's customer ID from the session cookie and query via `event.context.admin` (which takes explicit IDs). This is sound for T01 and sidesteps the race. The platform-side fix is out of T01's scope — flagged as carry-over for post-Phase-2 work.
- **CORS middleware ordering.** Nitro loads middleware alphabetically: `cors.ts` < `plan-limits.ts` < `tenant.ts`. `event.context.merchant` isn't populated yet when CORS runs. Solved by having CORS call `resolveMerchant(event)` directly — the LRU-cached result means the tenant middleware's subsequent call is a hash hit.
- **CommerceAdapter shape.** T01's example used `adapter.catalog.getProducts` (namespaced); the actual `CommerceAdapter` interface is flat (`adapter.getProducts`). Implementations use the flat form, matching the `packages/nuxt` reference.

**Deferred (by design; not blocking)**:

- Zod validation. Dashboard doesn't carry zod as a dep; inline checks suffice for T01's MVP. Can revisit when T02 formalises the contract for the `@commercejs/nuxt` remote-mode client.
- Additional composable-covered routes (forgot/reset password, addresses, reviews, returns, wishlist, promotions, countries). Not in T01's action-item list; add in a follow-up if T02 needs them.
