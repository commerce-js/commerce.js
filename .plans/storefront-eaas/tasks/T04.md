# T04: Hosted SSR as second Fly.io process

---

**Status**: ✅ **Completed** (2026-04-15; deployed and verified live on Fly.io)
**Effort**: Medium
**Blocked By**: T01, T02, T03

## Goal

Run `apps/storefront` as a second process inside the existing `commercejs-cloud` Fly.io app.
Requests to `*.commercejs.cloud` (non-`app.`) are routed to the storefront process; requests
to `app.commercejs.cloud` continue to the dashboard process. Merchants get full SSR at their
subdomain with zero extra Fly apps.

## Context

This is Layer 3 of the three-layer model. The storefront process (port 3001) runs alongside the
dashboard process (port 3000) and worker (port N/A) in the same Fly VM. A hostname-routing
middleware in the dashboard's Nitro server acts as the proxy: if the request host is
`app.commercejs.cloud`, it falls through to the dashboard normally; for any other host, it
proxies to port 3001.

Why not a second Fly app? The wildcard cert and DNS wildcard (`*.commercejs.cloud`) already
point to this app. Splitting across two apps would require routing at the Fly edge or a
separate proxy tier. The single-app approach keeps deployment, secrets, and cert management
in one place.

The storefront process in this mode does NOT use `remoteApiBase` — it calls the dashboard API
on localhost (`http://localhost:3000/api/storefront/*`) to avoid external round-trips. The
tenant context is established by the dashboard's tenant middleware on the API side; the
storefront is a pure render layer.

## Requirements

### 1. Storefront build output in Dockerfile

Add a second `nuxt build` step for the storefront after the dashboard build:

```dockerfile
# Build storefront
RUN pnpm --filter '@commercejs/storefront...' --filter '!@commercejs/storefront' build  # deps first
RUN pnpm --filter @commercejs/storefront build

# Final image gets both outputs
COPY --from=builder /app/apps/storefront/.output /app/apps/storefront/.output
```

The storefront output goes to `/app/apps/storefront/.output/server/index.mjs`.

### 2. `fly.toml` storefront process

```toml
[processes]
  web    = "node apps/dashboard/.output/server/index.mjs"
  store  = "node apps/storefront/.output/server/index.mjs"
  worker = "node apps/dashboard/.output/worker.mjs"
```

The store process must listen on a different port:
```
NUXT_PORT=3001  # or via runtimeConfig
```

Set via `[env]` in `fly.toml` scoped to the `store` process.

### 3. Hostname proxy middleware in dashboard

The dashboard Nitro server gets a new early middleware that intercepts requests destined for
merchant subdomains and proxies them to the storefront process:

```ts
// apps/dashboard/server/middleware/storefront-proxy.ts
import { proxyRequest } from 'h3'

const STOREFRONT_PORT = process.env.STOREFRONT_PORT ?? '3001'
const STOREFRONT_ORIGIN = `http://localhost:${STOREFRONT_PORT}`

export default defineEventHandler(async (event) => {
  const host = getRequestHost(event, { xForwardedHost: true }).split(':')[0]

  // Dashboard host — fall through
  if (!host || host === (process.env.COMMERCEJS_BASE_HOST ?? 'commercejs.cloud')) return
  if (PLATFORM_HOSTS.has(host)) return

  // Merchant subdomain or custom domain — proxy to storefront process
  return proxyRequest(event, `${STOREFRONT_ORIGIN}${event.path}`, {
    // Forward original host so storefront can still read it for tenant-aware rendering
    headers: { 'X-Forwarded-Host': host },
  })
})
```

**Ordering note**: This middleware must run BEFORE the tenant middleware so control-DB routes
on `app.commercejs.cloud` aren't accidentally proxied. Nitro runs middleware in filename-alpha
order — name it `00.storefront-proxy.ts` or use `server/middleware/` ordering.

### 4. Storefront tenant awareness (render side)

In the storefront process, pages need the merchant context (name, locale, currency, theme) for
SSR. Two options:

- **Option A (preferred)**: The storefront's `merchant-config.ts` server plugin (from T03)
  reads the host from the incoming request and calls `http://localhost:3000/api/storefront/store`
  — which goes through the dashboard's tenant middleware — to load store info per-request or
  at process startup per-tenant.

- **Option B**: The storefront process reads `CONTROL_DATABASE_URL` directly and does its own
  tenant lookup. More coupling, not recommended.

Use Option A. The call is localhost (sub-millisecond) and the result can be cached in an LRU.

### 5. Process health probes

`fly.toml` health checks currently probe `/api/_health` which is on the `web` process.
Add a separate health route for the `store` process:

```ts
// apps/storefront/server/api/_health.get.ts
export default defineEventHandler(() => ({ ok: true }))
```

Update `fly.toml`:
```toml
[[services]]
  processes = ["store"]
  [[services.http_checks]]
    path = "/api/_health"
```

### 6. Environment variables

In the storefront process, `NUXT_COMMERCE_REMOTE_API_BASE` should NOT be set (that's for
standalone self-hosted). Instead, the storefront calls the local dashboard API. Set:

```
STOREFRONT_PORT=3001
NUXT_COMMERCE_API_BASE=http://localhost:3000/api/storefront  # local, no proxy needed
NUXT_SESSION_PASSWORD=<same as dashboard>  # for shared buyer sessions if needed
```

These are set as `fly.toml` process-scoped env vars.

**Live at**: `https://smoke.commercejs.cloud/` → storefront SSR, `https://app.commercejs.cloud/` → dashboard.

**What was implemented**:

Shipped in two commits: `12ab355` (initial architecture) + `4091a68` (five follow-ups after Fly surfaced real issues).

Topology:

```
Fly edge :443
     │
     ▼
/bin/bash scripts/start-web.sh  (tini → supervisor)
     ├── node .output/server/index.mjs            :3000  dashboard
     │    └ server/middleware/00.storefront-proxy.ts
     │      - /api/* → dashboard
     │      - host ∈ PLATFORM_HOSTS → dashboard
     │      - else → proxyRequest(http://localhost:3001…, X-Forwarded-Host)
     │
     └── node apps/storefront/.output/server/index.mjs :3001  storefront
          └ @commercejs/nuxt remote mode, NUXT_COMMERCE_REMOTE_API_BASE=http://localhost:3000/api/storefront

            - T02 proxy forwards to dashboard :3000 with x-forwarded-host
              re-injected from AsyncLocalStorage (set by proxy-forwarded-host plugin)
```

**Challenges encountered** (each cost a deploy cycle):

- **Prisma 7 strict env resolution.** `packages/platform/prisma.config.ts` calls `env('DATABASE_URL')` which now hard-errors if unset. The dashboard step already had an `NEON_CONTROL_DB_URL` placeholder; the platform step needed its own. Not T04-specific — it would've bit the next dashboard-only deploy too.
- **dash doesn't implement `wait -n`.** `node:22-slim`'s `/bin/sh` is dash. The supervisor was written assuming bash-level features — `wait -n` for "block until ANY child exits". On Fly the machine rebooted instantly into a crash loop with `Illegal option -n`. Switched shebang + fly.toml invocation to `/bin/bash` (bash is in the base image).
- **Build-time vs runtime env var for remote mode.** `NUXT_COMMERCE_REMOTE_API_BASE` is set in `fly.toml [env]` so it's present at runtime but NOT during `nuxt build` in the Dockerfile. The initial `isRemote = !!remoteApiBase` check failed at build time, so the storefront image still registered the adapter plugin — which tried to initialise a Salla adapter at runtime and crashed every request with "SALLA_TOKEN required". Fixed by keying on `options.apiRoutes === false` (set explicitly in storefront's nuxt.config.ts) — stable across build/runtime.
- **Nuxt's in-process `$fetch` drops both event.context and x-forwarded-host.** This was the fight of the deploy. The proxy handler is invoked by `useFetch('/api/storefront/*')` during SSR through Nitro's local fetch path; the inner event's Host is `localhost` and has none of the outer request's headers. Tried: header options on proxyRequest (event-scoped, wrong event), `event.context.xForwardedHostOriginal` (Nuxt doesn't forward event.context across the boundary — logged as `fromContext: undefined`). AsyncLocalStorage works — the outer request enters a store frame via Node's async_hooks that all nested async code inherits. The proxy reads from it and falls back to the current event only for non-SSR callers (curl hitting `/api/storefront/*` directly on :3001). Localhost noise from internal dispatches is filtered so it can't overwrite the outer merchant host.
- **Nitro SWR multi-tenant leak.** `routeRules['/'] = { swr: 3600 }` cached the first merchant's rendered HTML and served it to every subdomain for the next hour. Nitro's SWR keys on path alone — no vary-by-host. Caught this with `curl nonexistent.commercejs.cloud/` showing "My Store" content (smoke's cache). Dropped SWR for pages; only static asset cache headers remain. Per-tenant cache key is a T04 follow-up.
- **Asset path collision on `/_nuxt/*`.** Both Nuxt apps default `app.buildAssetsDir` to `/_nuxt/` and emit differently-hashed bundles. The storefront's HTML references e.g. `/_nuxt/entry.DBq-o-HX.css`, but on the shared-machine deploy that URL first hits the dashboard's Nitro public-assets handler, which only has the dashboard's `entry.DXLwi2pn.css` and 404s without falling through to the storefront-proxy middleware. Result: a fully unstyled storefront on `smoke.commercejs.cloud` despite correct SSR HTML. Fixed by giving the storefront its own asset namespace — `app.buildAssetsDir: '/_storefront/'` in `apps/storefront/nuxt.config.ts`. Storefront URLs are now `/_storefront/entry.<hash>.css`, the dashboard's `/_nuxt/**` handler never matches, and the proxy middleware routes them to `:3001` cleanly. Extends naturally to per-theme namespaces (`/_themes/<name>/`) when we add template themes.
- **Decision to co-supervise instead of splitting processes.** Fly's native `[processes]` model spawns separate machine pools per process group — which means `localhost` won't cross between dashboard and storefront; they'd have to call each other via `.internal` DNS. Chose single-machine supervisor instead: matches T04's spec literally, no DNS plumbing, sub-ms in-process hop, one health check covers both halves via `start-web.sh` teardown. Trade-off: scaling is coupled (can't scale storefront independently of dashboard) and any crash restarts both. Revisit when SSR load diverges from API load.

**Deferred (by design; not blocking T04's completion)**:

- Per-tenant SSR cache — add x-forwarded-host to Nitro's cache key so the storefront can restore SWR without cross-tenant bleed. Meanwhile every page is fresh-SSR'd (~0.3–2.5s TTFB).
- Unknown-merchant 404 early — dashboard's 00.storefront-proxy middleware currently lets any non-platform host through to the storefront, which renders a generic "CommerceJS" shell when the API 404s. Cheap to fix by resolving the merchant in the middleware before proxying.
- useCart / 6 `useAdapter()` composables still need rework against T01's session-based storefront API (carry-over from T03).
- Separating storefront into its own Fly process group when/if SSR load justifies independent scaling.
