# T03: `apps/storefront` — Fly.io migration

---

**Status**: ✅ **Completed** (2026-04-15; built + ran against live `smoke.commercejs.cloud`)
**Effort**: Small
**Blocked By**: T01 (needs a live `/api/storefront/*` endpoint to point at)

## Goal

Migrate `apps/storefront` from the `cloudflare-pages` Nitro preset to `node-server`, wire it
to the hosted API via `remoteApiBase`, and verify a clean production build so it's ready to be
added as a second Fly.io process in T04.

## Context

`apps/storefront` was built for the Cloudflare Pages era. It uses `preset: 'cloudflare-pages'`
in `nuxt.config.ts` and has a `wrangler.toml`. On the `fly/eaas` branch, everything runs on
standard Node.js. The storefront needs the same treatment the dashboard got in Step 1.

After this task, the storefront can be pointed at the live `commercejs-cloud` API
(`acme.commercejs.cloud/api/storefront`) in remote mode. In T04, it gets embedded as a second
process in the same Fly app.

## Requirements

### 1. Nitro preset swap

```ts
// apps/storefront/nuxt.config.ts
nitro: {
  preset: 'node-server',   // was 'cloudflare-pages'
}
```

Remove `wrangler.toml` from `apps/storefront/`.

### 2. Switch to remote API mode

Point the storefront at the live API using T02's `remoteApiBase` config:

```ts
// nuxt.config.ts
commerce: {
  apiRoutes: false,
  apiBase: '/api/storefront',
  // remoteApiBase set via env: NUXT_COMMERCE_REMOTE_API_BASE
},
```

At build time and in Fly secrets, set:
```
NUXT_COMMERCE_REMOTE_API_BASE=https://acme.commercejs.cloud/api/storefront
NUXT_COMMERCE_API_KEY=cjs_live_xxx   # merchant's API key
```

For the hosted EaaS case (T04), `REMOTE_API_BASE` will not be needed — the storefront
process will call the API process on localhost. This env var is only for standalone / self-hosted.

### 3. Merchant config injection

The storefront needs to know the merchant's store name, currency, locale, and theme at
server-start time. Add a Nitro server plugin that loads store config on startup:

```ts
// apps/storefront/server/plugins/merchant-config.ts
export default defineNitroPlugin(async () => {
  // On process start, fetch store info from the API
  // Cache in memory — refreshed on restart
  // Exposed via useRuntimeConfig().public.store
})
```

This populates `<title>`, OG tags, currency formatter, and RTL flag without a per-request DB hit.

### 4. RTL / locale support

The storefront's `app.config.ts` and `nuxt.config.ts` should read `locale` from the injected
merchant config. Arabic (`ar-SA`) → add `dir="rtl"` to `<html>`. Already has the Tailwind RTL
setup; just needs the locale wiring.

### 5. Remove Cloudflare dependencies

- Delete `apps/storefront/wrangler.toml`
- Remove `@cloudflare/workers-types` from devDependencies if present
- Remove `cloudflare-pages` from `nitro.preset` (step 1)

### 6. Build verification

`pnpm --filter @commercejs/storefront build` must succeed and emit `.output/server/index.mjs`.

## Execution Summary

**Completed**: 2026-04-15

**What was implemented**:

- **`apps/storefront/nuxt.config.ts`** — Nitro preset `cloudflare-pages` → `node-server`; commerce config switched to remote mode (`apiRoutes: false`, `apiBase: '/api/storefront'`); stripped the CF-era `runtimeConfig.public.store` block (see "Challenges" for why).
- **`apps/storefront/wrangler.toml`** — deleted.
- **`apps/storefront/server/plugins/merchant-config.ts`** (new) — Nitro boot plugin that resolves `NUXT_COMMERCE_REMOTE_API_BASE`, pings `${remote}/store`, and logs one line per merchant so Fly/systemd logs show what tenant a process is wired to. Warns (not throws) on upstream failure so a transient network blip during boot doesn't put the process in a crash loop.
- **`apps/storefront/app/app.vue`** — wraps root with `useHead({ htmlAttrs: { lang, dir } })` derived from `useStoreInfo()`. First HTML byte carries the correct language + direction for Arabic merchants; no flash of LTR before hydration.
- **`apps/storefront/app/composables/useLocalizedString.ts`** — reads the active locale from `useStoreInfo()` instead of a hardcoded `'en'`, so localized product/category names resolve to the merchant's default locale.
- **`apps/storefront/.env`** — purged the CF-era `COMMERCE_ADAPTER=platform` + raw DB URL; added `NUXT_COMMERCE_REMOTE_API_BASE` pointing at the live smoke tenant.
- **`apps/storefront/package.json`** — `build` no longer runs platform DB migrations (nonsensical in remote mode); added `start` script for `node .output/server/index.mjs`.

**Verification**:

Live against `smoke.commercejs.cloud` via `NUXT_COMMERCE_REMOTE_API_BASE=https://smoke.commercejs.cloud/api/storefront node .output/server/index.mjs`:

- Process boot log: `[storefront] Connected to https://smoke.commercejs.cloud/api/storefront — merchant="My Store" locale=en dir=ltr`
- `GET /` → 200, 32.5 KB HTML with `<html lang="en" dir="ltr">` and `<title>My Store — Premium Storefront</title>`
- `GET /products` → 200, 29.6 KB
- `GET /api/storefront/cart` → 200, cart auto-created via the proxy to the hosted API
- `GET /api/storefront/products` → 200, paged upstream result forwarded intact
- `GET /api/storefront/store` → 200, hosted store config forwarded intact

**Challenges encountered**:

- **`runtimeConfig.public` is frozen at runtime.** The first cut of the merchant-config plugin tried to mutate `runtime.public.store = { name, locale, dir }` so `app.vue` could read it synchronously via `useRuntimeConfig()`. That throws `Cannot assign to read only property 'store'` because Nuxt seals public runtime config at Nitro boot. Dropped that approach — the plugin is now log-only, and `app.vue` reads from `useStoreInfo()` whose `useFetch('commerce:store')` is cached per SSR pass (single upstream lookup per render, the module's proxy + Nitro handle it). No measurable cost vs. the attempted runtimeConfig cache.
- **Cart composable URL shape mismatch.** `@commercejs/nuxt`'s `useCart` expects `${apiBase}/cart/{cartId}/items` (cartId-in-URL), but T01's hosted API is session-based (`${apiBase}/cart/items`, cartId on the cookie). The layout only reads reactive state (`cart`, `itemCount`) so the homepage renders cleanly; actual add-to-cart / update-quantity flows will 404 against the proxy until the composable is reworked. **Deferred** — tracked as the same follow-up as the six `useAdapter()`-based composables from T02 (useReviews, useReturns, useWishlist, usePromotions, useBrands, useLocations). The session-based storefront API is the correct long-term shape; the composables need to migrate to match.
- **Cloudflare devDep audit.** `package.json` had no `@cloudflare/workers-types`. Verified via grep — only the `wrangler.toml` file itself and the `nitro.preset` value referenced Cloudflare, both now gone.

**Deferred (by design; not blocking T04)**:

- Cart / checkout composables rework to match T01's session-based contract.
- The six `useAdapter()` composables that need to migrate off the in-process adapter (useReviews, useReturns, useWishlist, usePromotions, useBrands, useLocations). `useBrands` and `useLocations` have matching `/api/storefront/*` endpoints already in T01 — quick wins.
- Full RTL verification against an Arabic merchant — smoke tenant has English as default locale. The plumbing is correct (`defaultLocale.code === 'ar' → dir='rtl'`) but hasn't been exercised against a real Arabic storefront.
- Fly deployment of the storefront as a standalone process — that's T04's hostname-proxied multi-process architecture.
