# T02: `@commercejs/nuxt` remote mode

---

**Status**: ✅ **Completed** (2026-04-15; verified live against `smoke.commercejs.cloud` and a local echo server)
**Effort**: Small
**Blocked By**: T01 (remote API endpoint must exist before testing the remote mode)

## Goal

Make `@commercejs/nuxt` work as a pure API client when `apiRoutes: false` — composables call
a remote `apiBase` URL (no local DB connection, no local route registration), and a built-in
server proxy handler eliminates CORS for client-side calls.

## Context

`@commercejs/nuxt` has two modes today:
- `apiRoutes: true` (default) — registers 46 local routes, needs a local DB connection
- `apiRoutes: false` — skips route registration, but composables still hit `apiBase` directly

The gap: when `apiRoutes: false` and `apiBase` is a remote URL (e.g.
`https://acme.commercejs.cloud/api/storefront`), client-side `$fetch` calls are cross-origin.
In full SSR (first load), calls are server-to-server — no CORS. On client-side navigation, the
browser makes cross-origin requests — blocked unless CORS is configured on both ends.

The clean fix: when `apiRoutes: false`, automatically register a thin local proxy route at the
same `apiBase` path that forwards to the configured remote URL. Browser always talks to same
origin; the Nuxt server forwards server-to-server.

## Requirements

### 1. Proxy route injection (when `apiRoutes: false`)

In `module.ts` setup, when `options.apiRoutes === false` and `options.apiBase` is a remote URL:

```ts
// Inject a catch-all proxy handler at the apiBase path
addServerHandler({
  route: `${options.apiBase}/**`,
  handler: resolve('./runtime/server/proxy'),
})
```

The proxy handler (`runtime/server/proxy.ts`):

```ts
export default defineEventHandler(async (event) => {
  const config = useRuntimeConfig(event)
  const target = config.commerce.remoteApiBase  // set from apiBase env var
  const path = event.path.replace(config.commerce.apiBase, '')
  return proxyRequest(event, `${target}${path}`, {
    headers: {
      'X-Commerce-Key': config.commerce.apiKey ?? '',
    },
  })
})
```

`proxyRequest` is a Nitro/h3 built-in — no extra deps.

### 2. Runtime config additions

Extend `CommerceModuleOptions` and the Nuxt `runtimeConfig` injection:

```ts
// New options
apiKey?: string          // injected as X-Commerce-Key on proxied requests
remoteApiBase?: string   // the actual remote URL (apiBase stays as local proxy path)
```

Env var mapping (standard Nuxt convention):
```
NUXT_COMMERCE_API_KEY=cjs_live_xxx
NUXT_COMMERCE_REMOTE_API_BASE=https://acme.commercejs.cloud/api/storefront
```

When `remoteApiBase` is set, `apiBase` defaults to `/api/storefront` (local proxy path) and
`apiRoutes` defaults to `false`. This makes the common self-hosted config one env var.

### 3. Module detection logic

```ts
// module.ts — in setup()
const isRemote = !!options.remoteApiBase
if (isRemote) {
  options.apiRoutes = false
  options.apiBase = options.apiBase ?? '/api/storefront'
  // Register proxy handler
  addServerHandler(...)
  // Inject remoteApiBase into private runtimeConfig
}
```

### 4. No change to composables

The 16 composables all call `apiBase` via `useFetch`/`$fetch`. Since the proxy lives at the
same local path, composables need zero changes. The proxy is transparent.

### 5. Documentation update

Update `packages/nuxt/README.md` with a "Self-hosted / remote API" section showing the two-line
config.

## Execution Summary

**Completed**: 2026-04-15

**What was implemented**:

- **`packages/nuxt/src/module.ts`** — added `remoteApiBase` and `apiKey` to `CommerceModuleOptions`. In `setup()`, detects remote mode from module options or `NUXT_COMMERCE_REMOTE_API_BASE` env var, then:
  - forces `apiRoutes = false`
  - sets `apiBase` default to `/api/storefront` (vs `/api/_commerce` in local mode)
  - skips `addServerPlugin(commerce-adapter)` — no DB / platform credentials needed
  - skips OpenAPI generation (no local routes to document)
  - registers a catch-all `addServerHandler({ route: '${apiBase}/**', handler: proxy })`
  - stashes `remoteApiBase`, `apiKey`, and the local `apiBase` prefix in private `runtimeConfig.commerce` (server-only)
- **`packages/nuxt/src/runtime/server/proxy.ts`** — the catch-all handler. Uses h3's `proxyRequest` to forward method/body/query/cookies upstream, injects `X-Commerce-Key` from private runtime config, and sets `cookieDomainRewrite: ''` to strip the upstream `Set-Cookie` `Domain=` attribute so buyer session cookies land on the self-hosted origin.
- **`packages/nuxt/playground/`** — minimal harness so `pnpm --filter @commercejs/nuxt dev` with `NUXT_COMMERCE_REMOTE_API_BASE` set boots a local Nuxt app that proxies to the remote.
- **`packages/nuxt/README.md`** — "Remote mode" section with the two-env-var setup and an updated config-interface block.

**Verification (live)**:

- Against `smoke.commercejs.cloud/api/storefront` via the playground:
  - `GET /api/storefront/products` → 200 `{items:[], total:0, …}` (matches direct upstream)
  - `GET /api/storefront/store` → 200 full store config
  - `GET /api/storefront/orders` → 401 with original error body forwarded
  - `GET /api/storefront/cart` → 200, auto-creates cart, `Set-Cookie: cjs-buyer-session=…; Max-Age=2592000; Path=/; HttpOnly; Secure` forwarded intact (cookie is `Secure` so curl over HTTP localhost doesn't persist it — expected)
  - Query params (`?page=1&perPage=5`) pass through; non-proxied paths (`/api/not-storefront/*`) are not intercepted
- Against a local Node echo server:
  - Path rewrite verified end-to-end (`/api/storefront/products?page=2` → upstream receives `/upstream/products?page=2`)
  - `X-Commerce-Key: test_apikey_abc123` injected on every proxied request
  - Direct (non-proxied) curl shows `apiKey: null` — no environmental leakage
  - POST with JSON body forwarded correctly

**Challenges encountered**:

- **Nuxt's `defaults` block is applied before `setup()`.** The first attempt kept `apiBase: '/api/_commerce'` as a flat default, so the remote-mode override `options.apiBase = options.apiBase || '/api/storefront'` was a no-op — the proxy mounted at `/api/_commerce/**` instead of `/api/storefront/**`. Fixed by removing `apiBase` from the `defaults` object entirely and resolving the mode-aware default inside `setup()` after the remote-mode check.
- **The 6 `useAdapter()`-based composables (useReviews, useReturns, useWishlist, usePromotions, useBrands, useLocations) will still break in remote mode** because they call the adapter directly on the server side. The majority of composables (useProducts, useProduct, useCart, useCheckout, useOrders, useCustomer, useStoreInfo, useCategories, useCountries, usePrice) already use `$fetch(apiBase)` and work through the proxy. Migrating the 6 holdouts is out of T02's action items — flagged below.
- **Cookie `Secure` flag.** The upstream sets `cjs-buyer-session` with `Secure`, so the cookie only round-trips over HTTPS. This is correct for prod (self-hosted merchants run HTTPS) but means dev-time testing requires a trusted cert on the local origin or temporarily stripping `Secure`. Not fixed in T02 — the bearer of this cookie is the upstream, not our code.

**Deferred (by design; not blocking)**:

- Migrating the 6 `useAdapter()` composables to `$fetch(apiBase)`. Tracked as a follow-up once the corresponding `/api/storefront/*` endpoints exist (some, like `/brands` and `/locations`, already exist in T01 — those are quick wins).
- `apps/storefront` config + e2e test. Defers to T03 which migrates storefront off `cloudflare-pages` to `node-server` (where remote mode is actually deployable).
- Unit tests for the proxy handler. The live playground test harness exercises the full code path including h3's cookie rewriting and path stripping; a unit test would mock `proxyRequest` and test less surface.
