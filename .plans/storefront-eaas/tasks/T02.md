# T02: `@commercejs/nuxt` remote mode

---

**Status**: 🟡 **Planned**
**Effort**: Small
**Blocked By**: T01 (remote API endpoint must exist before testing the remote mode)

## Goal

Make `@commercejs/nuxt` work as a pure API client when `apiRoutes: false` — composables call
a remote `apiBase` URL (no local DB connection, no local route registration), and a built-in
server proxy handler eliminates CORS for client-side calls.

## Context

`@commercejs/nuxt` has two modes today:
- `apiRoutes: true` (default) — registers 46 local routes, needs a local DB connection
- `apiRoutes: false` — skips route registration, but composables still hit `apiBase` directly

The gap: when `apiRoutes: false` and `apiBase` is a remote URL (e.g.
`https://acme.commercejs.cloud/api/storefront`), client-side `$fetch` calls are cross-origin.
In full SSR (first load), calls are server-to-server — no CORS. On client-side navigation, the
browser makes cross-origin requests — blocked unless CORS is configured on both ends.

The clean fix: when `apiRoutes: false`, automatically register a thin local proxy route at the
same `apiBase` path that forwards to the configured remote URL. Browser always talks to same
origin; the Nuxt server forwards server-to-server.

## Requirements

### 1. Proxy route injection (when `apiRoutes: false`)

In `module.ts` setup, when `options.apiRoutes === false` and `options.apiBase` is a remote URL:

```ts
// Inject a catch-all proxy handler at the apiBase path
addServerHandler({
  route: `${options.apiBase}/**`,
  handler: resolve('./runtime/server/proxy'),
})
```

The proxy handler (`runtime/server/proxy.ts`):

```ts
export default defineEventHandler(async (event) => {
  const config = useRuntimeConfig(event)
  const target = config.commerce.remoteApiBase  // set from apiBase env var
  const path = event.path.replace(config.commerce.apiBase, '')
  return proxyRequest(event, `${target}${path}`, {
    headers: {
      'X-Commerce-Key': config.commerce.apiKey ?? '',
    },
  })
})
```

`proxyRequest` is a Nitro/h3 built-in — no extra deps.

### 2. Runtime config additions

Extend `CommerceModuleOptions` and the Nuxt `runtimeConfig` injection:

```ts
// New options
apiKey?: string          // injected as X-Commerce-Key on proxied requests
remoteApiBase?: string   // the actual remote URL (apiBase stays as local proxy path)
```

Env var mapping (standard Nuxt convention):
```
NUXT_COMMERCE_API_KEY=cjs_live_xxx
NUXT_COMMERCE_REMOTE_API_BASE=https://acme.commercejs.cloud/api/storefront
```

When `remoteApiBase` is set, `apiBase` defaults to `/api/storefront` (local proxy path) and
`apiRoutes` defaults to `false`. This makes the common self-hosted config one env var.

### 3. Module detection logic

```ts
// module.ts — in setup()
const isRemote = !!options.remoteApiBase
if (isRemote) {
  options.apiRoutes = false
  options.apiBase = options.apiBase ?? '/api/storefront'
  // Register proxy handler
  addServerHandler(...)
  // Inject remoteApiBase into private runtimeConfig
}
```

### 4. No change to composables

The 16 composables all call `apiBase` via `useFetch`/`$fetch`. Since the proxy lives at the
same local path, composables need zero changes. The proxy is transparent.

### 5. Documentation update

Update `packages/nuxt/README.md` with a "Self-hosted / remote API" section showing the two-line
config.
