# T03: Tap subscription billing

---

**Status**: 🟡 **Planned**
**Effort**: Large — spawns `.plans/tap-billing/plan.md` when started.
This file is a pointer + scope anchor.
**Blocked By**: T02 (trial-ending emails + invoice receipts).

## Goal

Charge merchants for using CommerceJS Cloud via Tap subscriptions.
Define plan tiers, integrate Tap's subscription APIs, handle
subscription-lifecycle webhooks, add merchant-admin UX for viewing
the current plan and invoices, and enforce plan limits on storefront
usage. Gates self-service signup (T04 needs the first-charge path).

## Context

- `Merchant.tapCustomerId` is already a column on the control DB,
  plumbed from the initial merchant-provisioner work.
- `apps/hosted-checkout` uses the Tap SDK for one-off commerce
  payments. The auth/SDK/webhook-verifier scaffolding is already
  proven in production. T03 layers subscription APIs on top of
  that same infrastructure.
- Merchants today exist but pay nothing — every account on smoke is
  free. Public signup (T04) cannot open until billing is live.
- No plan tiers exist yet. T03 defines them: likely a Free / Starter /
  Growth / Enterprise ladder with differentiation on product count,
  order volume, custom domain, API rate limits.
- T02's trial-ending email + order confirmation (invoice receipts)
  are dependencies. T02 landing before T03 keeps the acceptance
  scenarios clean.

## Requirements

**T03 operates in sub-plan mode.** The first session that starts T03
creates `.plans/tap-billing/plan.md` following the merchant-admin-
followup structure.

### Scope anchor (must be in the sub-plan)

**Data model** (1 sub-task):
- Control DB: new tables for `plan_tiers` (seeded constants), and
  `merchant_subscriptions` (status, Tap subscription id, current
  period start/end, plan tier ref, trial end). Prisma-only (control
  DB is not parity-tracked).
- Migration via `apps/dashboard/prisma/schema.prisma` + `prisma migrate
  deploy` at build time.

**Tap subscription wiring** (~3 sub-tasks):
- `createSubscription` — at signup or on plan-upgrade. Creates a Tap
  subscription object, stores ref on `merchant_subscriptions`.
- `updateSubscription` — plan change (upgrade/downgrade), proration
  policy (immediate credit on upgrade, end-of-cycle downgrade).
- `cancelSubscription` — merchant-initiated OR admin-forced (past-due
  threshold exceeded). Grace period before storefront disable.

**Webhook handler** (1 sub-task):
- `POST /api/webhooks/tap/subscription` on the dashboard, HMAC-verified
  via `@commercejs/webhook-verifier`.
- Events: `subscription.activated`, `subscription.past_due`,
  `subscription.cancelled`, `invoice.paid`, `invoice.failed`.
- Each updates `merchant_subscriptions` status + enqueues side
  effects (T02 invoice-receipt email, trial-ending cron, etc.).

**Merchant admin UX** (~2 sub-tasks):
- `/admin/billing` page — current plan, next billing date, invoice
  history. Upgrade/downgrade button.
- `/admin/billing/invoices/[id]` — detail view with download link.

**Plan enforcement** (1 sub-task):
- Middleware on `/api/admin/products` (create), order creation, and
  API key limits that checks `merchant.plan.limits` before proceeding.
- Soft enforcement first (log + warn header); hard enforcement after
  smoke validation.

**Trial handling** (1 sub-task):
- 14-day free trial on signup (configured per plan tier).
- Cron emits `trial.ending` events at 7 + 1 days remaining → enqueues
  T02's trial-ending email.
- Trial expiry → auto-convert to paid OR cancel (depending on whether
  a payment method was captured).

### Out of scope for T03 (deferred)

- **Usage-based billing** (per-order fees, per-API-call fees). T03
  ships flat-rate only. `.plans/usage-billing/` TBD.
- **Multi-currency billing**. SAR only in v1 (Bahrain region primary
  market). FX handling deferred.
- **Dunning flows** — limited to "retry 3 times, then cancel" for v1.
  Full dunning (failed-charge email sequences, grace periods with
  merchant notification) is a v2 concern.
- **Annual plans / prepay discounts**. Monthly only in v1.
- **Tax computation on invoices**. VAT/WHT is Tap's responsibility for
  v1; platform doesn't add on top.
- **Refund UI for merchant plan charges**. Manual via Tap console.
- **Admin-side merchant plan override** (discount / comp) — direct DB
  edits only in v1.

## Test Scenarios

Exercised in the sub-plan. Summary:

- [ ] Smoke merchant on Free tier, creates 51st product → rate-limit
      response with upgrade link.
- [ ] Upgrade from Free to Starter via `/admin/billing` → Tap charges,
      webhook updates `merchant_subscriptions.status=active`, feature
      limits relax.
- [ ] Downgrade from Starter to Free at period end → prorated credit
      applied at next invoice, not immediate.
- [ ] Failed charge → webhook flips to `past_due` → 3 retries by Tap
      → final-failure webhook → `cancelled` → merchant sees grace-period
      warning, then storefront disables.
- [ ] Trial-ending 7-day warning email arrives on schedule (uses T02).
- [ ] Invoice receipts arrive on successful charge (uses T02).
- [ ] Webhook replay protection: same `invoice.paid` event twice →
      idempotent update, no double-credit.
- [ ] Cross-tenant webhook spoof → HMAC verification rejects.

## Implementation Notes

- **Sub-plan first rule.** Same as T02 — run Phase 1–3 of
  structured-plan-mode against `.plans/tap-billing/` before any code.
  Research phase should explicitly validate Tap supports subscriptions
  (not just one-off charges) — some regional providers don't.
- **Sandbox discipline.** Tap has a sandbox mode; NEVER charge
  production keys during development or CI. Document the switch in
  `.secrets` with a big banner.
- **Idempotent webhooks.** Every webhook handler must be safe to
  receive the same event twice (Tap will retry on timeout). Use the
  webhook event id as a dedupe key.
- **Plan tier constants vs. rows.** Seeded rows on `plan_tiers` is
  more flexible but needs a seed script. TypeScript constants are
  simpler but require a deploy to change pricing. Decide in sub-plan.
- **Smoke merchant migration.** Existing smoke merchant should land
  on a Free-tier subscription post-T03 — either grandfather manually
  or use the signup flow (T04 dependency).
