# T05: `fly/eaas → main` branch-swap

---

**Status**: 🟡 **Planned**
**Effort**: Small (1 session, ~2–4 hours elapsed, one-shot destructive
op on GitHub)
**Blocked By**: T01 + T02 + T03 + T04 all shipped + deployed + smoke
acceptance green.

## Goal

Cut `main` over to the tip of `fly/eaas` so the canonical branch
reflects the live production code. After this task, Cloudflare-era
code (`packages/cloud/`, the Drizzle-active ORM wiring on main, the
`@nuxthub/core` dependencies on main) is archived or deleted.
`CLAUDE.md` updates to drop the two-branch guidance. Every future
Claude session starts from `main` and doesn't need the branch-matrix
context.

## Context

- `fly/eaas` has accumulated ~6 months of commits since the Cloudflare
  → Fly.io pivot. `main` is frozen on the Cloudflare-era code that's
  not running in production.
- Per the `feedback_git_merge_over_rebase` memory, the user defaults
  to merge over rebase when syncing. But this isn't a sync — it's a
  one-time cutover of the branch that represents "production source
  of truth."
- Two tactical options (decide in the task):
  - **Fast-forward merge `main ← fly/eaas`** — preserves `main`'s
    history linearly. Works if `main` hasn't diverged with its own
    commits (need to check `git log main..fly/eaas` and
    `git log fly/eaas..main`).
  - **Hard reset `main` to `fly/eaas` tip** — drops Cloudflare-era
    `main` history. Force-push required. Preserves nothing.
- Both options need careful coordination if external consumers (CI,
  npm publishes, deploys, docs site) track `main`.

## Requirements

**This is a destructive op with blast radius beyond local changes.
Per `CLAUDE.md`'s "Executing actions with care" section, every step

### 0. Pre-flight — audit what tracks `main`

- CI workflows in `.github/workflows/*.yml` — which trigger on `main`?
- npm publish — does `.github/workflows/release.yml` use `main`?
- Deploy automation — if any `main` push triggers Fly deploys, swap
  WILL cause a production redeploy. Coordinate timing.
- Docs site build (`apps/docs`) — branch tracker?
- External repo consumers — does anyone `git clone` our repo and
  expect `main` to be the authoritative branch?

Write findings to this task file before proceeding.

### 1. Decide: fast-forward vs. hard-reset

Run:
```bash
git log main..fly/eaas --oneline | wc -l    # commits on fly/eaas not on main
git log fly/eaas..main --oneline | wc -l    # commits on main not on fly/eaas
```

If the second count is 0 → fast-forward is safe. If nonzero → the
commits on `main` need to be preserved somewhere (archive branch?
cherry-pick? evaluate each).

Default assumption: hard-reset with an archive branch for history
preservation.

### 2. Create `archive/cloudflare-main` branch

Before any destructive op:
```bash
git checkout main
git branch archive/cloudflare-main
git push origin archive/cloudflare-main
```

This preserves every `main` commit as a named reference. Anyone who
needs the Cloudflare era can check it out.

### 3. Reset `main` to `fly/eaas` tip

```bash
git checkout main
git reset --hard fly/eaas
git push origin main --force-with-lease
```

**`--force-with-lease`**, not `--force` — refuses the push if the
remote has diverged since our last fetch. Safety net.

### 7. Delete `fly/eaas` branch


Optional — could be left as a dead reference. Default: delete, since
`main` now tracks what `fly/eaas` used to.

## Implementation Notes

- **`--force-with-lease`, always.** Never `--force` without the
  `-with-lease` safety net. The one-line cost is a sanity check
  against someone else's unobserved push; the savings on a botched
  swap are enormous.
- **Archive branch is mandatory.** Even if the team decides the
  Cloudflare code has zero remaining value, the 30 seconds to create
  an archive branch are free insurance.
- **Sequence the comms carefully.** If anyone else has uncommitted
  local work on top of old `main`, they need to reset their local
  branch after the swap. Notify BEFORE.
- **`fly/eaas` branch deletion is optional but recommended.** Keeping
  it around invites confusion — "wait, which is current?" Delete to
  remove the ambiguity.
- **This task file should itself be on `main` after the swap.** Which
  means the commit that writes T05's Execution Summary is the same
  commit as the `main`-reset. Careful ordering:
  1. Do audit (action items up to step 3).
  2. Create archive branch.
  3. Reset main to fly/eaas. This commit is fly/eaas's tip.
  4. All subsequent commits happen on `main`.
  5. Write the Execution Summary + other cleanups as a final commit
     on `main`.
