# T04: Step 9 self-service signup

---

**Status**: 🟡 **Planned**
**Effort**: Medium (estimated 3–5 days, 3–4 commits)
**Blocked By**: T02 (email verify + welcome) and T03 (first-charge on
subscription creation).

## Goal

Ship the public-facing `app.commercejs.cloud/signup` flow so a
stranger can go from landing page to a provisioned storefront with
admin access in under 5 minutes. Translates Step 9 of
`.plans/fly-migration-plan.md` from architectural-intent notes into
merchant-admin-style task decomposition + code. This is the last
launch-blocking workstream.

## Context

- The merchant-provisioner (`apps/dashboard/server/utils/merchant-
  provisioner.ts`) already creates a Neon branch + admin_user +
  storefront for a new merchant. Operator dashboard uses it today.
  T04 exposes it to the public via a guided signup flow.
- `Merchant` + `Domain` tables on the control DB are ready to accept
  public signups. What's missing: the signup form, the plan-picker,
  the Tap subscription step, the email verification step, and the
  first-login redirect.
- T02 provides welcome + verification emails. T03 provides the
  subscription-creation endpoint. T04 stitches them into a flow.
- Unlike T02/T03, T04 is small enough to live entirely in this plan's
  task directory — no sub-plan spawned.

## Requirements

### 1. Signup form — `/signup` on `app.commercejs.cloud`

- Fields: email, password (8+), merchant name, preferred subdomain
  (validated against existing merchants), plan tier selection.
- Client-side validation + Zod on submit.
- Pre-flight: check subdomain availability, email uniqueness.
- CSRF protection on the route (first route that accepts anonymous
  POST with side effects).

### 2. Plan picker UX

- Reads plan tiers from T03's `plan_tiers` table (or constants).
- Displays pricing, feature matrix, trial terms.
- Defaults to recommended plan (probably Starter).
- Tap card-capture step (reuses hosted-checkout's card element).
- Skip card for Free tier (if Free tier exists post-T03).

### 3. Account creation pipeline

- Server-side handler `/api/public/signup.post.ts`:
  1. Validate input (Zod).
  2. Check subdomain + email uniqueness against control DB.
  3. Create `Merchant` row with `status='provisioning'`,
     `tapCustomerId=null`.
  4. Create Tap subscription via T03's APIs → store
     `tapSubscriptionId` + trial end.
  5. Enqueue `provision-store` BullMQ job (existing worker handles
     Neon branch + admin_user + storefront seed).
  6. Enqueue T02 welcome email + verification email jobs.
  7. Return `{ merchantId, provisioningStatus }` to the client.

### 4. Provisioning status polling

- Client-side: `/signup/provisioning?merchantId=...` polls
  `/api/public/signup/status?merchantId=...` every 2s.
- Page shows progress (account created → subscription active →
  storefront provisioning → done) with a playful copy.
- On success, shows "Check your inbox to verify your email" with
  a link to `/admin/login`.

### 5. Email verification

- T02 sends email with signed-URL token.
- `/verify?token=...` route on storefront (or dashboard — decide
  during T04).
- Marks `Merchant.emailVerifiedAt` on control DB.
- Unverified merchants have a banner on `/admin` urging verification;
  no hard enforcement in v1.

### 6. First-login redirect

- After verification, the admin redirect lands on the merchant's
  `*.commercejs.cloud/admin` with a one-time `?welcome=1` query that
  shows a tour modal.
- Tour modal points to Products, Orders, Theme, Settings. Link to
  docs.

### 7. Error paths

- Tap card decline → show inline error, keep form state, let retry.
- Subdomain claimed between pre-flight and submit → show "already
  taken, pick another" + suggest variations.
- Provisioning job fails → poll endpoint returns `failed` with
  support contact; no charge if provisioning didn't complete (T03
  handles compensation).

## Test Scenarios

- [ ] Happy path: new email + new subdomain + valid card → merchant
      provisioned, two emails arrive (welcome + verify), admin
      accessible on new subdomain.
- [ ] Duplicate email → 409 with "already registered, sign in"
      instead.
- [ ] Subdomain already claimed → 409, form suggests alternatives.
- [ ] Card decline → stays on form, shows decline reason, card
      re-entry works.
- [ ] Network flake mid-signup → polling page recovers, no
      double-provisioning.
- [ ] Click verification link → `emailVerifiedAt` set, banner
      dismisses.
- [ ] Click verification link twice → second click no-ops (idempotent).
- [ ] Abandoned signup (created but never verified after 72h) →
      cleanup cron removes the merchant row (or flags for review —
      decide in T04).
- [ ] Rate-limit on signup endpoint rejects >10 req/min per IP.
- [ ] First-login `?welcome=1` shows tour, subsequent visits don't.

## Implementation Notes

- **Stays in this plan** — no sub-plan spawn. Medium effort, clear
  scope, reuses a lot of existing infrastructure.
- **Rate limiting is mandatory** — public unauthenticated signup is
  a classic abuse vector. Fly.io's edge or BullMQ-backed counter;
  decide during implementation. Don't skip.
- **Abandoned signups policy** — if a merchant signs up but never
  verifies, after 72h do we delete? Keep? Mark? Pre-commit answer:
  delete the Merchant row + Neon branch + admin_user to recover
  the subdomain. Flag in the task for review before shipping.
- **Subdomain validation** — enforce a blocklist
  (`www`, `app`, `admin`, `checkout`, `api`, `smoke`, ...). Merchant-
  accessible subdomain slugs must not collide with platform surfaces.
- **Mobile-first design** — the signup page is the first impression;
  it must look good on a phone. Desktop comes second.
- **Step 9 update** — `.plans/fly-migration-plan.md` has Step 9 as
  🔲 Backlog. T04 flips it to ✅ in the same commit as the task
  completion.
