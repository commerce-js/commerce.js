# T02: Transactional emails

---

**Status**: 🟡 **Planned**
**Effort**: Large — spawns `.plans/transactional-emails/plan.md` when
started. This file is a pointer + scope anchor.
**Blocked By**: None — independent, but gates T03 and T04.

## Goal

Wire the `handleSendEmail` BullMQ stub in `apps/dashboard/worker.ts`
through to Resend (via the already-published
`@commercejs/notification-resend` provider), ship the first set of
transactional templates (staff invite, password reset, order
confirmation, welcome, email verification, trial-ending), and retrofit
every surface that should send email to enqueue a job. Unblocks T09's
email-invite flow (still deferred), gates T03 (trial-ending + receipts),
gates T04 (signup verification + welcome).

## Context

Email infrastructure has been parked since the worker shipped:

- `apps/dashboard/worker.ts` has a `handleSendEmail` stub that takes
  a job payload and logs a TODO.
- `@commercejs/notification-resend` is a published provider package
  (0.x series) implementing the notification-provider interface.
  Ready to consume.
- T09 explicitly deferred the email-invite flow (see
  `.plans/merchant-admin-followup/plan.md` Out of Scope) with the
  promise that the "email-workstream plan" would pick it up. This is
  that plan.
- Tap billing (T03) needs trial-ending emails (7-day, 1-day warnings)
  and invoice receipts — one of T02's templates.
- Self-service signup (T04) needs a welcome email and an email-verify
  flow — two more T02 templates.

### Scope anchor (must be in the sub-plan)

**Provider wiring** (1 sub-task):
- Replace `handleSendEmail` stub with a real dispatcher that calls
  `@commercejs/notification-resend`'s send method.
- Environment variables: `RESEND_API_KEY`, `RESEND_FROM_ADDRESS` (at
  minimum). Surface via `fly secrets`.
- BullMQ retry policy: 3 attempts, exponential backoff (matches the
  existing `dispatch-webhook` job).
- Add a "send test email" button to the platform-operator dashboard
  (not merchant admin) for on-demand verification.

**Templates** (6 sub-tasks, one per template minimum):
1. **Staff invite** — completes T09's deferred flow. Token-based
   accept-invite page on the merchant admin, email delivers the
   signed URL. Introduces a `staff_invites` table on the merchant
   branch DB.
2. **Password reset** — for both merchant admins AND buyer customers.
   Two separate templates, two separate reset routes.
3. **Order confirmation** — customer-facing, sent on order creation
   (hosted-checkout finalize).
4. **Welcome** — sent on successful merchant signup (gates T04).
5. **Email verification** — sent on signup + on email change.
   Double-opt-in pattern.
6. **Trial-ending** — sent 7 days + 1 day before a trial expires
   (gates T03).

**Retrofit** (N sub-tasks, one per trigger point):
- `/api/admin/auth/login/forgot` (new) → password reset email
- `/api/storefront/auth/password-reset` (if it exists; check) → buyer
  reset email
- `order.created` domain event → order confirmation
- `admin.auth.createAdmin` with `sendInvite: true` flag → staff
  invite
- Signup flow completion (T04 will trigger this) → welcome + verify
- Billing cron (T03 will trigger this) → trial-ending

**Testing**:
- Sandbox email inbox for dev/CI (Resend has a test domain).
- Feature-flag-gated sends in smoke so acceptance doesn't spam a real
  address.
- Template snapshot tests (render HTML to string, compare against
  golden).

### Out of scope for T02 (deferred)

- Marketing/lifecycle emails (newsletters, re-engagement). Transactional
  only.
- SMS/WhatsApp notifications (different provider stack).
- Open/click tracking (Resend supports it; v2 with `.plans/email-
  analytics/`).
- Multi-language email content — v1 ships English, with a TODO for
  Arabic when product demand warrants it.
- User preferences / unsubscribe UX — transactional emails are
  service-critical and don't need opt-out in v1.

## Implementation Notes

- **Sub-plan first rule.** Before writing any code, run the
  Phase 1–3 of the structured-plan-mode skill on
  `.plans/transactional-emails/`. The sub-plan research should
  confirm Resend is still the right pick (vs. SES, Postmark,
  Sendgrid) at this point in time.
- **Template location decision** happens in the sub-plan. Either
  co-locate in `apps/dashboard/server/emails/*.ts` (simple, app-
  specific) or package as `@commercejs/email-templates` (reusable,
  but premature abstraction for v1). Default to co-located.
- **Staff invites schema change**: the `staff_invites` table lands on
  the merchant DB (Prisma + Drizzle, parity + idempotent lazy-migrate
  — same pattern T09's `admin_users.status` and T13's `activity_events`
  used). Sub-plan sub-task.
- **Timing**: trial-ending emails need a cron-driven BullMQ scheduler
  (repeatable jobs). This is new infra — call it out in the sub-plan.
