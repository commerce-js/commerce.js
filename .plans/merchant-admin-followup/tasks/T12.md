# T12: Storefront theming (CSS custom properties v1)

---

**Status**: ✅ **Completed (2026-04-20)**
**Effort**: Large
**Blocked By**: None.

## Goal

A logged-in merchant can set their brand's primary and accent colors, font
family, and hero image from `/admin/theme`. Changes apply to the
storefront at `*.commercejs.cloud` on the next request — no redeploy,
no build step. v1 ships CSS custom properties injection; full Tailwind
preset compilation is explicitly deferred to v2.

## Context

Nothing theme-related exists on `AdminAPI` or the storefront today.
Merchants run unstyled-by-default `@nuxt/ui` with the repo's Tailwind
defaults. T12 adds minimal per-merchant visual identity — enough to
make `smoke.commercejs.cloud` look different from
`another-merchant.commercejs.cloud` without a storefront code change.

## Requirements

### 1. Schema — merchant branch DB

Add to the existing `store_info` (or equivalent) table on both Prisma and
Drizzle:

- `primaryColor` (string, hex, nullable)
- `accentColor` (string, hex, nullable)
- `fontFamily` (string, e.g. `'Inter'` or `'Cairo'`, nullable)
- `heroImageUrl` (string, nullable — URL to a Tigris-hosted image)
- `heroHeadingEn` (string, nullable)
- `heroHeadingAr` (string, nullable)

One migration, both backends, `check-query-parity.sh` green.

### 2. Platform — type extension

Add the same fields to `StoreSettings` in
`packages/platform/src/admin/types.ts`. `admin.getStoreSettings()` and
`admin.updateStoreSettings()` automatically pass them through (T06's
form may optionally gain these fields too — see "Scope split decision"
below).

### 3. Scope split decision — settings vs theme page

Two options, decide during T12 kickoff:

- **(a) Fold into T06 settings page** — add a "Brand & theme" tab to
  `/admin/settings.vue`. Fewer pages; tighter UX.
- **(b) Separate `/admin/theme.vue`** — dedicated page with colour
  pickers and live-preview card. Better surface for the colour-picker
  UX; clearer sidebar nav entry.

Default recommendation: **(b)** for v1, because theming is a distinct
mental model ("what does my store LOOK like") from settings ("what
currency and contact info"). Reversible.

### 4. Admin page (`/admin/theme.vue`)

Fields:

- Primary colour — colour picker (native `<input type="color">` is
  sufficient v1; fancy pickers are v2).
- Accent colour — same.
- Font family — dropdown of curated options + "custom" string input.
  Curated: Inter, Cairo, Tajawal, Noto Kufi Arabic, system-ui.
- Hero image — upload via T04 presigned flow (`context: 'theme'`), key
  `merchants/${id}/theme/${uuid}/${filename}`.
- Hero heading EN + AR (two text inputs with `dir` set appropriately).
- **Live preview card** — renders a mini-storefront-header with the
  chosen colors and heading so the merchant sees the effect before
  saving.

Save → `PATCH /api/admin/settings` (reuses T06's route) with the theme
fields.

### 5. Storefront consumer — Nitro plugin

New file at `apps/storefront/server/plugins/theme-inject.ts`:

- Hook into `render:html` (Nitro's HTML render hook).
- Read the resolved merchant from `event.context.merchant` (the tenant
  middleware already sets this — same plumbing as the dashboard).
- Fetch `storeInfo` from `event.context.db` once per request (or
  cache per-request via context).
- Inject a `<style>` block into the rendered `<head>`:

  ```css
  :root {
    --cjs-primary: <primaryColor or Tailwind primary fallback>;
    --cjs-accent: <accentColor or fallback>;
    --cjs-font: <fontFamily or 'system-ui'>;
  }
  body { font-family: var(--cjs-font), system-ui, sans-serif; }
  ```

- If `heroImageUrl` is set, expose it as a prop / runtime config readable
  by the homepage component for rendering the hero banner.

### 6. Storefront consumers — UI bits

Update `apps/storefront/app/pages/index.vue` (or the hero component) to:

- Read `heroImageUrl` + `heroHeadingEn` / `heroHeadingAr` from
  `useStoreInfo()`.
- Render a hero banner at the top (image as background, heading
  centered) ONLY when `heroImageUrl` is set; otherwise fall back to the
  existing header.

Optionally sprinkle `bg-[var(--cjs-primary)]` or `text-[var(--cjs-primary)]`
arbitrary-value classes into CTAs where the primary color should show
(e.g. "Add to cart" button). v1 need not rewire every colour; even one
or two high-visibility touchpoints demonstrate the system.

### 7. Sidebar link

Add "Theme" to `apps/storefront/app/layouts/admin.vue`.

## Implementation Notes

- **CSS-vars-only v1**: Tailwind preset injection (per-tenant compiled
  CSS with custom classes like `bg-brand-500`) is explicitly v2. It
  requires a storefront build-pipeline change (per-merchant Tailwind
  config) that's an engineering bet of its own.
- **Colour accessibility**: don't expose `textOnPrimary` — just pick a
  sensible default (white vs black based on contrast) in the plugin, or
  let the merchant accept default-text behavior. v1.
- **Font loading**: if the merchant picks a non-system font, emit a
  `<link rel="preload" as="font" …>` or a Google Fonts `<link>` in the
  plugin. Document the FOUT tradeoff in the page help text.
- **Caching**: the plugin reads storeInfo per request — acceptable for
  v1 volume. If this becomes a hotspot, LRU-cache by merchant ID on the
  process (invalidate on any `updateStoreSettings` write).
- **Nonexistent tenants**: the plugin must no-op gracefully when
  `event.context.merchant` is absent (platform hosts, health-check
  paths). Don't throw.

## Execution Summary

**Completed**: 2026-04-20

**What was implemented**:
- **Platform schema** — 6 new columns on `store_info` (`primary_color`,
  `accent_color`, `font_family`, `hero_image_url`, `hero_heading_en`,
  `hero_heading_ar`) on both Prisma and Drizzle schemas, with matching
  idempotent `ALTER TABLE … ADD COLUMN IF NOT EXISTS` statements in both
  `migratePrisma()` and `migrateDrizzle()` so pre-existing merchant Neon
  branches pick up the columns on the next request (lazy-migrate — same
  pattern T09 established for `admin_users.status`). Drizzle migrate also
  gets the `admin_users.status` ADD COLUMN patch that T09 had only added to
  Prisma, which restores the Drizzle integration-test suite to green.
- **@commercejs/types** — `StoreTheme` interface added (primaryColor,
  accentColor, fontFamily, heroImageUrl, heroHeadingEn, heroHeadingAr, each
  `Maybe<string>`); `StoreInfo.theme?: Maybe<StoreTheme>` on the public
  store type. Adapters that don't surface theming simply omit the field.
- **Platform public domain** — `domains/store.ts` gets a `mapStoreTheme`
  helper that returns `null` when every token is unset (so the storefront
  falls back to defaults) and a populated `StoreTheme` when any token is
  set. Existing fields are untouched.
- **Platform admin types + store domain** — `StoreSettings` and
  `UpdateStoreInput` each get 6 flat fields (matching the T06 shape).
  `admin.updateStoreSettings` treats an empty string on any theme field as
  a valid clear (persists `null`), and leaves `undefined` fields
  completely untouched. Unit-tested both branches.
- **Platform unit tests** — new `__tests__/admin-store-theme.test.ts`
  covers six scenarios: null mapping, populated mapping, full-round-trip
  write, empty-string-clear, undefined-omit, and the public-domain
  null-vs-populated split (7 tests, all green).
- **Dashboard schema** — `updateStoreSettingsSchema` in
  `apps/dashboard/server/utils/admin-schemas.ts` extended with 6 zod
  validators: color strings capped at 64 chars, font-family at 128, URL
  check on heroImageUrl, headings at 200. Empty string accepted on every
  field to support the clear path. No new routes — reuses the existing
  `/api/admin/settings.{get,patch}` endpoints.
- **Storefront theming** — `apps/storefront/app/app.vue` gets a new
  `useHead({ style: [...] })` block that injects a `:root { --cjs-primary:
  …; --cjs-accent: …; --cjs-font: …; } body { font-family: var(--cjs-font),
  … }` `<style>` tag (key `cjs-theme`) into `<head>` on every SSR render.
  The theme data comes from the already-fetched `useStoreInfo()` call —
  no extra upstream round-trip. Missing tokens are omitted, so any
  `bg-[var(--cjs-primary)]` / `var(--cjs-primary, var(--ui-primary))`
  consumer falls back cleanly. **Deviation from T12.md**: the spec called
  for a Nitro `render:html` plugin that reads `event.context.db` — but
  the storefront on `fly/eaas` is a pure remote-mode client (no DB
  connection), so a Nitro plugin would just re-fetch data the Vue layer
  already has. Using `useHead` is the semantically equivalent, simpler
  path that ships one `<style>` tag in `<head>` identically.
- **Homepage hero** — `apps/storefront/app/pages/index.vue` renders a
  full-bleed themed hero (image + Arabic/English headline picked via the
  merchant's default locale) when `theme.heroImageUrl` is set, and
  otherwise falls back to the original gradient hero — but with the
  merchant's `heroHeadingEn/Ar` substituted in when available. Both
  variants use `var(--cjs-primary, var(--ui-primary))` on the "Shop Now"
  CTA — one high-visibility touchpoint demonstrating the CSS-var system
  without rewiring every color.
- **Admin UI** — new page `/admin/theme.vue`: two-column layout (form
  left, sticky live-preview card right), native `<input type="color">`
  paired with a text input so both the swatch picker and hex paste-ins
  work, curated font-family dropdown (Inter / Cairo / Tajawal / Noto Kufi
  Arabic / system-ui) with a "Custom…" escape for free-form strings, hero
  image upload reusing T04's presigned-PUT flow (`context: 'theme'`),
  Arabic heading input with `dir="rtl"`, reset-to-defaults button,
  dirty-snapshot tracking, sticky save bar matching T06, ⌘/Ctrl+S
  keyboard shortcut, and beforeunload + route-leave guards. Sidebar gets a
  "Theme" link (swatch icon) between Staff and Settings.
- **Build + parity** — `pnpm build` green on `@commercejs/types`,
  `@commercejs/platform`, `@commercejs/nuxt`, `apps/dashboard`,
  `apps/storefront`. `check-query-parity.sh` still green (151/151).

**Challenges encountered**:
- **Storefront lacks `event.context.db`.** The T12 spec called for a
  Nitro plugin reading the per-tenant theme record off `event.context.db`
  — but on `fly/eaas` the storefront process is a pure remote-mode client
  (NUXT_COMMERCE_REMOTE_API_BASE proxies to the dashboard on the same
  machine), so it has no DB connection of its own. The storefront's
  existing `useStoreInfo()` call already fetches StoreInfo via the
  dashboard's tenant middleware; piping theme data through the same
  `StoreInfo.theme` field and injecting `<style>` via `useHead` gives the
  same render-time result with one less fetch per request.
- **Drizzle seed failure on pre-existing test DB.** The initial Drizzle
  integration test run failed with "column primary_color of relation
  store_info does not exist" because `migrateDrizzle()` uses
  `CREATE TABLE IF NOT EXISTS` — a no-op on a persistent test DB that
  already has the table. Added idempotent `ALTER TABLE … ADD COLUMN IF
  NOT EXISTS` patches at the end of `migrateDrizzle` (mirroring the
  pattern T09 set up on `migratePrisma`). Took the opportunity to
  back-fill the `admin_users.status` patch T09 had missed on the Drizzle
  side.
