# T13: Audit log / activity feed

---

**Status**: ✅ **Completed** (2026-04-20)
**Effort**: Small/Medium
**Blocked By**: ~~T09~~ — unblocked 2026-04-20.

## Goal

Every mutation that a merchant's staff performs on the admin API writes
a row to an `activity_events` table on the merchant's branch DB. A new
`/admin/activity` page renders a timeline of those events — "Alice
fulfilled order ORD-…", "Bob changed primary color to #22c55e",
"Charlie deleted product …". Provides audit trail + "who did what"
answers without support-ticket round-trips.

## Context

Not on the parent plan's original Out-of-Scope list, but surfaced as
scope-adjacent by the plan's research: T09 makes multi-staff work
practical, and multi-staff without an audit log is a support-ticket
generator. Small/Medium effort because:

- One new table + one migration (both drivers).
- One middleware hook helper (`recordActivity`).
- One paginated read endpoint + one timeline page.

## Requirements

### 1. Schema — merchant branch DB

New `activity_events` table:

| Column | Type | Notes |
|---|---|---|
| `id` | ULID/UUID | PK |
| `actorId` | string (FK → `admin_users.id`) | nullable: system actions set null |
| `actorEmail` | string | snapshot at time of event (for display after the actor is deleted) |
| `action` | string | e.g. `'order.fulfilled'`, `'product.created'`, `'settings.updated'` |
| `entityType` | string | e.g. `'order'`, `'product'`, `'settings'` |
| `entityId` | string \| null | the affected row |
| `diff` | json \| null | optional — shape `{ before: {...}, after: {...} }` for key fields |
| `createdAt` | datetime | default now() |

Indexes on (`createdAt desc`), (`actorId`), (`entityType`, `entityId`).

One migration, both drivers, `check-query-parity.sh` green.

### 2. Platform — new methods

Append to `AdminAPI` (and platform domain):

```ts
interface AdminAPI {
  recordActivity(input: {
    actorId: string | null
    actorEmail: string
    action: string
    entityType: string
    entityId?: string | null
    diff?: object | null
  }): Promise<void>

  listActivity(params?: {
    page?: number
    perPage?: number
    actorId?: string
    entityType?: string
    from?: string
    to?: string
  }): Promise<PaginatedResult<ActivityEvent>>
}
```

`recordActivity` is append-only; never read-modify-write. `listActivity`
uses the shared `parseFromBound` / `parseToBound` helpers.

### 3. Platform — call sites

Instrument every existing mutation to call `recordActivity`:

**T01–T05 mutations** (fill retroactively):
- `admin.createProduct` → `product.created`
- `admin.updateProduct` → `product.updated`
- `admin.deleteProduct` → `product.deleted`
- `admin.fulfillOrder` → `order.fulfilled`
- `admin.refundOrder` → `order.refunded`

**T06–T12 mutations** (add as each task ships; T13 just enforces the
pattern in the shared helper):
- `admin.updateStoreSettings` → `settings.updated`
- `admin.deleteCustomer` → `customer.deleted`
- `admin.{create,update,delete}Category` → `category.*`
- `admin.auth.{createAdmin,deleteAdmin,updateAdmin,changePassword}` →
  `staff.*`
- `admin.updateInventory` → `inventory.updated`

Approach: the **dashboard HTTP route** calls `recordActivity` after a
successful platform call. Don't bake it into the platform domain methods
directly — keep platform driver-neutral and let the dashboard layer
supply the actor-from-session context.

Helper at `apps/dashboard/server/utils/audit.ts`:

```ts
export async function recordActivity(event: H3Event, action: string, entityType: string, entityId?: string, diff?: object) {
  const admin = event.context.admin
  const session = await getMerchantSession(event)
  await admin.recordActivity({
    actorId: session?.adminId ?? null,
    actorEmail: session?.email ?? 'system',
    action, entityType, entityId: entityId ?? null, diff: diff ?? null,
  }).catch(() => { /* fire-and-forget; don't fail the mutation if audit write fails */ })
}
```

Each mutation route calls `await recordActivity(event, ...)` after the
successful platform call.

### 4. API route

- `apps/dashboard/server/api/admin/activity.get.ts` — `?page=&perPage=&actorId=&entityType=&from=&to=`
  → `admin.listActivity(params)`.

Gated by `requireMerchantSession`.

### 5. Page (`/admin/activity.vue`)

Timeline grouped by day. Each row: actor email, action verb (humanized —
`'fulfilled order ORD-123'`), relative time ("2 hours ago"), optional
link to the entity (if `entityType` has a corresponding admin page).

Filters at top:
- Actor dropdown (from `admin.auth.listAdmins()`).
- Entity type dropdown.
- Date range.

Pagination.

### 6. Humanization

Human-readable action strings live in a small map in
`apps/storefront/app/composables/useActivityLabel.ts`:

```ts
'order.fulfilled' → 'fulfilled order'
'order.refunded'  → 'refunded order'
'product.created' → 'created product'
// ...
```

Fallback: the raw action string (don't crash on unknown keys).

### 7. Sidebar link

Add "Activity" to `apps/storefront/app/layouts/admin.vue`.

## Implementation Notes

- **Fire-and-forget**: `recordActivity` failure must not cause the
  business-layer mutation to fail. Wrap in `.catch(() => {})` at the
  helper level. Worst case an audit row is missing; the business state
  is still consistent.
- **Diff payloads**: don't record full entity snapshots — that bloats
  the table. Store only the changed keys ("status: 'pending' → 'shipped'").
  For small mutations (delete, status change) the diff is tiny; for
  large updates (product update with many fields), store only the
  changed keys.
- **Retention**: v1 keeps events forever. A retention policy (e.g. delete
  events older than 2 years) is a v2 concern.
- **Permissions**: all staff can read the activity log in v1. A
  role-restricted view (owner-only) could ship later.

## Execution Summary

**Completed**: 2026-04-20

**What was implemented**:
- Platform: new `activity_events` table (id/actorId/actorEmail/action/
  entityType/entityId/diff/createdAt) with three indexes (createdAt DESC,
  actorId, entityType+entityId) on both Prisma + Drizzle schemas.
  Idempotent `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`
  in both `migratePrisma` and `migrateDrizzle` — lazy-migrates onto
  pre-existing merchant Neon branches on first request (same pattern
  T09/T12 used).
- Platform: `AdminAPI.recordActivity` (append-only) + `AdminAPI.listActivity`
  (paginated, filterable by actorId/entityType/date range — reuses
  `parseFromBound/parseToBound`). New `admin/activity.ts` domain +
  `ActivityEvent` / `RecordActivityInput` / `ListActivityParams` types
  in `admin/types.ts`. Query parity 153/153. 9 unit tests cover
  record-forward, list pagination/filters, perPage clamping (DEFAULT=50,
  MAX=200), offset math, and the deleted-actor snapshot path.
- Dashboard: `apps/dashboard/server/utils/audit.ts` — fire-and-forget
  helper reading `getMerchantSession(event)` (userId + email map to
  the snapshot columns), wrapping `admin.recordActivity` in try/catch
  so an audit-write failure NEVER fails the business mutation.
- Dashboard: `/api/admin/activity.get.ts` Zod-validated (actorId,
  entityType, from, to, page, perPage) + `requireMerchantSession`-gated;
  `listActivityQuerySchema` added to `admin-schemas.ts`.
- Dashboard: 15 existing mutation routes retrofitted to call
  `recordActivity` AFTER the successful platform call — products
  (create/update/delete), orders (fulfill/refund), categories
  (create/update/delete), customers (delete), inventory (update),
  settings (update), staff (create/update/delete/change-password).
  Diff payloads store `changedKeys` arrays or single-field context
  (trackingNumber, role, etc.) — never full entity snapshots.
- Admin UI: `/admin/activity.vue` timeline grouped by day
  (Today/Yesterday/dated). Each row: actor email + humanized verb +
  entity badge + entity link (products/orders/customers/categories/
  staff) + relative time. Filters: actor dropdown (from `/api/admin/staff`),
  entityType dropdown, date-range preset (7d/30d/90d/all/custom) — matches
  T11 analytics UX. `UPagination` at 50/page.
- Admin UI: `useActivityLabel` composable — small action→verb map with
  raw-action fallback so future tasks adding new action keys never
  crash the page.
- Sidebar: "Activity" link (clock icon) between Theme and Settings.

**Challenges encountered**:
- **Sentinel values for USelect** — Reka UI's `<SelectItem>` reserves the
  empty string for "clear selection". Two separate files needed the
  same pattern: `/admin/activity.vue` uses `'all'` for actor + entity
  filters, `/admin/theme.vue` uses `'__default__'` for the "System
  default" font option. Out-of-scope fixes to `theme.vue` and
  `products/index.vue` landed in a separate commit (`963a125`) after
  the main T13 wiring. Same pattern T08 used for category parents —
  worth promoting to a shared helper if a third consumer appears.
- **Deleted-actor rendering** — `actor_id` is not FK-cascaded in the
  schema (intentional — deleting the admin must not delete audit rows).
  When an admin is deleted, past rows keep pointing at the orphan UUID.
  The UI renders the snapshotted `actorEmail` correctly, but the
  "deleted" chip only lights up on `!actorId` (system actions). A
  secondary mechanism (cross-check against live admin list to tag
  orphaned rows) would be a v2 polish — acceptable v1 since the email
  snapshot is the primary display signal.
- **Fire-and-forget test** — couldn't cleanly inject a runtime failure
  in production without a redeploy loop. Validated instead via (1)
  code inspection of the helper's blanket `try { } catch { }` wrapper,
  (2) 9 unit tests including one that verifies recordActivity with null
  actorId and null diff, (3) 5 live mutation→audit pairs on smoke all
  returning 200 with audit rows landing. Semantics are structurally
  correct — the helper always resolves void.
- **Lazy-migrate pattern confirmed resilient to CREATE TABLE** — T09
  + T12 exercised this for `ADD COLUMN IF NOT EXISTS`. T13 is the
  first live test of `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF
  NOT EXISTS` on a pre-existing branch. First `/api/admin/activity`
  request returned `total:0` + HTTP 200 on smoke's 3-day-old branch —
  no manual migration step, no error.

**Deviations from T13.md spec**:
- `ActivityEvent` type lives in `packages/platform/src/admin/types.ts`
  (re-exported from `@commercejs/platform`) rather than
  `@commercejs/types`. Rationale: purely platform-admin concern — no
  external adapter / UI component needs it. Avoids a `types → core →
  platform` rebuild cascade on a type that has no cross-package
  consumers. Same call pattern T12's `StoreTheme` went the other
  direction for (cross-package consumer) — T13's scope is narrower so
  local-to-platform is the right call.
- Audit helper reads session via `getMerchantSession(event)` and maps
  `userId → actorId`, `email → actorEmail`. T13.md showed a bespoke
  `session.adminId / session.email` shape but `merchant-session.ts`
  already exposes `userId + email` with identical semantics.
