# T13: Audit log / activity feed

---

**Status**: 🟡 **Planned**
**Effort**: Small/Medium
**Blocked By**: T09 (needs multi-staff to have meaningful actor attribution).

## Goal

Every mutation that a merchant's staff performs on the admin API writes
a row to an `activity_events` table on the merchant's branch DB. A new
`/admin/activity` page renders a timeline of those events — "Alice
fulfilled order ORD-…", "Bob changed primary color to #22c55e",
"Charlie deleted product …". Provides audit trail + "who did what"
answers without support-ticket round-trips.

## Context

Not on the parent plan's original Out-of-Scope list, but surfaced as
scope-adjacent by the plan's research: T09 makes multi-staff work
practical, and multi-staff without an audit log is a support-ticket
generator. Small/Medium effort because:

- One new table + one migration (both drivers).
- One middleware hook helper (`recordActivity`).
- One paginated read endpoint + one timeline page.

## Requirements

### 1. Schema — merchant branch DB

New `activity_events` table:

| Column | Type | Notes |
|---|---|---|
| `id` | ULID/UUID | PK |
| `actorId` | string (FK → `admin_users.id`) | nullable: system actions set null |
| `actorEmail` | string | snapshot at time of event (for display after the actor is deleted) |
| `action` | string | e.g. `'order.fulfilled'`, `'product.created'`, `'settings.updated'` |
| `entityType` | string | e.g. `'order'`, `'product'`, `'settings'` |
| `entityId` | string \| null | the affected row |
| `diff` | json \| null | optional — shape `{ before: {...}, after: {...} }` for key fields |
| `createdAt` | datetime | default now() |

Indexes on (`createdAt desc`), (`actorId`), (`entityType`, `entityId`).

One migration, both drivers, `check-query-parity.sh` green.

### 2. Platform — new methods

Append to `AdminAPI` (and platform domain):

```ts
interface AdminAPI {
  recordActivity(input: {
    actorId: string | null
    actorEmail: string
    action: string
    entityType: string
    entityId?: string | null
    diff?: object | null
  }): Promise<void>

  listActivity(params?: {
    page?: number
    perPage?: number
    actorId?: string
    entityType?: string
    from?: string
    to?: string
  }): Promise<PaginatedResult<ActivityEvent>>
}
```

`recordActivity` is append-only; never read-modify-write. `listActivity`
uses the shared `parseFromBound` / `parseToBound` helpers.

### 3. Platform — call sites

Instrument every existing mutation to call `recordActivity`:

**T01–T05 mutations** (fill retroactively):
- `admin.createProduct` → `product.created`
- `admin.updateProduct` → `product.updated`
- `admin.deleteProduct` → `product.deleted`
- `admin.fulfillOrder` → `order.fulfilled`
- `admin.refundOrder` → `order.refunded`

**T06–T12 mutations** (add as each task ships; T13 just enforces the
pattern in the shared helper):
- `admin.updateStoreSettings` → `settings.updated`
- `admin.deleteCustomer` → `customer.deleted`
- `admin.{create,update,delete}Category` → `category.*`
- `admin.auth.{createAdmin,deleteAdmin,updateAdmin,changePassword}` →
  `staff.*`
- `admin.updateInventory` → `inventory.updated`

Approach: the **dashboard HTTP route** calls `recordActivity` after a
successful platform call. Don't bake it into the platform domain methods
directly — keep platform driver-neutral and let the dashboard layer
supply the actor-from-session context.

Helper at `apps/dashboard/server/utils/audit.ts`:

```ts
export async function recordActivity(event: H3Event, action: string, entityType: string, entityId?: string, diff?: object) {
  const admin = event.context.admin
  const session = await getMerchantSession(event)
  await admin.recordActivity({
    actorId: session?.adminId ?? null,
    actorEmail: session?.email ?? 'system',
    action, entityType, entityId: entityId ?? null, diff: diff ?? null,
  }).catch(() => { /* fire-and-forget; don't fail the mutation if audit write fails */ })
}
```

Each mutation route calls `await recordActivity(event, ...)` after the
successful platform call.

### 4. API route

- `apps/dashboard/server/api/admin/activity.get.ts` — `?page=&perPage=&actorId=&entityType=&from=&to=`
  → `admin.listActivity(params)`.

Gated by `requireMerchantSession`.

### 5. Page (`/admin/activity.vue`)

Timeline grouped by day. Each row: actor email, action verb (humanized —
`'fulfilled order ORD-123'`), relative time ("2 hours ago"), optional
link to the entity (if `entityType` has a corresponding admin page).

Filters at top:
- Actor dropdown (from `admin.auth.listAdmins()`).
- Entity type dropdown.
- Date range.

Pagination.

### 6. Humanization

Human-readable action strings live in a small map in
`apps/storefront/app/composables/useActivityLabel.ts`:

```ts
'order.fulfilled' → 'fulfilled order'
'order.refunded'  → 'refunded order'
'product.created' → 'created product'
// ...
```

Fallback: the raw action string (don't crash on unknown keys).

### 7. Sidebar link

Add "Activity" to `apps/storefront/app/layouts/admin.vue`.

## Implementation Notes

- **Fire-and-forget**: `recordActivity` failure must not cause the
  business-layer mutation to fail. Wrap in `.catch(() => {})` at the
  helper level. Worst case an audit row is missing; the business state
  is still consistent.
- **Diff payloads**: don't record full entity snapshots — that bloats
  the table. Store only the changed keys ("status: 'pending' → 'shipped'").
  For small mutations (delete, status change) the diff is tiny; for
  large updates (product update with many fields), store only the
  changed keys.
- **Retention**: v1 keeps events forever. A retention policy (e.g. delete
  events older than 2 years) is a v2 concern.
- **Permissions**: all staff can read the activity log in v1. A
  role-restricted view (owner-only) could ship later.
