CommerceJS is organized as a layered architecture where each package has a single responsibility. The packages compose together through well-defined interfaces.

## System Architecture

::system-architecture


The architecture is layered by responsibility. The **Unified Data Model** defines a shared vocabulary across all domains. The **Orchestration** engine routes requests to the correct adapter and payment provider. The **Integration Layer** translates between your application and any external platform, gateway, or webhook source.

## Design Principles

### Adapter Pattern

The `CommerceAdapter` interface defines how storefronts talk to eCommerce backends. Each platform (Salla, Shopify, WooCommerce) provides an adapter that maps its API to the unified types. The built-in `@commercejs/platform` adapter provides a Neon Postgres-powered commerce engine with an Admin API and Profile system.

### Orchestrator Pattern

The `CommerceOrchestrator` extends the adapter concept with a **three-tier domain model** and composable architecture. Domains are organized by how commonly they're needed:

| Tier | Domains | Required? |
|---|---|---|
| **Universal** | `catalog`, `store` | ✅ Always present |
| **Common** | `cart`, `checkout`, `orders`, `customers`, `wishlist`, `reviews`, `promotions`, `brands`, `countries`, `locations` | Optional |
| **Specialized** | `returns`, `wholesale`, `auctions`, `rentals`, `giftCards` | Optional |

```ts
import { createOrchestrator } from '@commercejs/core'

const orchestrator = createOrchestrator({
  name: 'my-store',
  catalog: myCatalogAdapter,
  store: myStoreAdapter,
  domains: {
    cart: myCartAdapter,
    orders: myOrderAdapter,
  },
})

// Type-safe domain access
if (orchestrator.supports('cart')) {
  const cart = await orchestrator.domain('cart').createCart()
}
```

### Domains vs Providers

CommerceJS distinguishes between two categories of functionality:

| Category | What It Is | Pattern | Examples |
|---|---|---|---|
| **Domain** | Data source — CRUD on entities | Adapter sub-interface | Catalog, Cart, Orders |
| **Provider** | Side-effect service — event-driven | Plugin registered in config | Payments, Notifications, Analytics |

**Domains** live on the adapter/orchestrator. **Providers** are registered in `createCommerce()` and wired to the event bus.

### Composition Patterns

CommerceJS supports two composition strategies:

**Composite Orchestrator** — source each domain from a different platform:

```ts
import { createCompositeOrchestrator } from '@commercejs/core'

const orchestrator = createCompositeOrchestrator({
  name: 'hybrid',
  providers: {
    catalog: shopifyAdapter,    // Products from Shopify
    store: shopifyAdapter,
    cart: platformAdapter,       // Cart from built-in engine
    customers: crmAdapter,       // Customers from CRM
  },
})
```

**Platform Fallback** — automatically fill missing domains with a fallback adapter:

```ts
import { withPlatformFallback } from '@commercejs/core'

// sallaAdapter has catalog + store, but no cart
// platformAdapter fills in cart, checkout, orders...
const orchestrator = withPlatformFallback(sallaAdapter, platformAdapter)
```

The `createCommerce()` engine wraps the adapter with capability routing, events, and multi-provider payments:

```ts
import { createCommerce } from '@commercejs/core'
import { SallaAdapter } from '@commercejs/adapter-salla'
import { TapPaymentProvider } from '@commercejs/payment-tap'

const commerce = createCommerce({
  adapter: new SallaAdapter({ token: '...' }),
  payments: { tap: new TapPaymentProvider({ secretKey: '...' }) },
  defaultPayment: 'tap',
})

const products = await commerce.getProducts({ query: 'shirt' })
// Returns SearchResult — same shape for Salla, Shopify, or any other platform
```

### Provider Interface

Payment providers implement the `PaymentProvider` interface. The checkout engine does not know or care which provider it uses:

```ts
interface PaymentProvider {
  createSession(input: CreatePaymentSessionInput): Promise<PaymentSession>
  confirmSession(sessionId: string): Promise<PaymentSession>
  refund(input: RefundInput): Promise<PaymentSession>
  verifyWebhook(event: PaymentWebhookEvent): Promise<boolean>
}
```

Swapping from Tap to Stripe requires changing one line — the provider instantiation.

### State Machine

The `CheckoutSession` uses a finite state machine to enforce valid checkout flows. Each state has defined transitions, and invalid transitions throw errors:

| State | Allowed Transitions | Triggered By |
|---|---|---|
| `idle` | `info` | `setCustomerInfo()` |
| `info` | `shipping` | `setShippingAddress()` |
| `shipping` | `payment` | `submitPayment()` |
| `payment` | `confirming`, `complete`, `failed` | `confirmPayment()`, webhook |
| `confirming` | `complete`, `failed` | Provider response |
| `failed` | `payment` | Retry |
| `complete` | — | Terminal |

## Layer Responsibilities

| Layer | Packages | Role |
|---|---|---|
| **Types** | `@commercejs/types` | Shared vocabulary — interfaces only, no runtime code |
| **Orchestration** | `@commercejs/core` | Engine — `createCommerce()`, orchestrator factories, event bus, webhook dispatch |
| **Checkout** | `@commercejs/checkout` | State machine — manages the checkout flow lifecycle |
| **Providers** | `payment-tap`, notifications, analytics | Side-effect services — payments, email, tracking |
| **Infrastructure** | `@commercejs/webhook-verifier` | Cross-cutting — security, verification |
| **Adapters** | `adapter-salla`, `platform` | Platform glue — maps external or built-in APIs to unified types |
| **Framework** | `@commercejs/nuxt` | Nuxt module — composables, server routes, runtime plugin |
| **Applications** | `hosted-checkout`, `storefront` | End-user apps — Nuxt applications |
