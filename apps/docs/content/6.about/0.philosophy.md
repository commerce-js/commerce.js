Every eCommerce project starts the same way: pick a platform, learn its API, build your storefront. Then requirements change — a new payment gateway, a different backend, a second market. Suddenly you are rewriting code that has nothing to do with your product.

Commerce.js exists to fix this.

## The Lock-In Problem

Platform APIs are not interchangeable. Salla returns `regular_price.amount`, Shopify returns `price` as a string, WooCommerce nests it inside `meta_data`. Your storefront code — the templates, the cart logic, the checkout flow — becomes tightly coupled to a single vendor.

Switching platforms means rewriting your data layer. Switching payment providers means rewriting your checkout. Even adding a second payment option requires forking your payment flow.

This is the vendor lock-in tax, and every team pays it eventually.

## Our Answer: Interfaces, Not Implementations

::adapter-pattern

Commerce.js introduces a thin abstraction layer between your application and the commerce backend. The abstraction has three parts:

### 1. Unified Types

A single set of TypeScript interfaces — `Product`, `Cart`, `Order`, `Customer` — that describe **what** commerce data looks like. Not how Salla stores it. Not how Shopify names it. Just the data.

Adapters translate between the platform's native format and these shared types. Your application code only sees the unified types and never touches platform-specific data.

### 2. Adapter Pattern

Each eCommerce platform implements the `CommerceAdapter` interface. The adapter is the only piece of code that knows about the platform's API. Everything above it — your storefront, your checkout, your analytics — is platform-agnostic.

Want to switch from Salla to Shopify? Swap one adapter. Your templates, your cart logic, your checkout — all untouched.

### 3. Payment Provider Interface

Payment gateways are separate from commerce platforms. A Salla store might use Tap, Stripe, or both. The `PaymentProvider` interface makes payment gateways pluggable and interchangeable.

The checkout state machine orchestrates the payment flow without knowing which provider it talks to. Adding a second payment option is one configuration change.

## Design Principles

### Ship Less Code

Every package in the monorepo has a single responsibility. `@commercejs/types` contains only interfaces — zero runtime code. `@commercejs/checkout` contains only the state machine. You install exactly what you need.

### Own Your Data

The `@commercejs/platform` package provides a built-in commerce engine backed by Neon Postgres. No external API calls, no vendor account required. Your data lives in a managed Postgres database.

This is not just for development. Embedded commerce — kiosks, desktop apps, offline-first stores — needs a backend that runs locally. Platform gives you one with zero configuration.

### Framework Agnostic, Framework Ready

The core packages work in any JavaScript runtime — Node.js, Deno, Edge Workers, the browser. The `@commercejs/nuxt` module then adds framework-specific niceties: auto-imported composables, server API generation, adapter injection.

The principle is simple: the engine should work everywhere, and the framework integration should feel like magic where you want it.

### Bilingual by Default

Commerce in the MENA region requires Arabic and English support at every level. The `LocalizedString` type — `string | Record<string, string>` — appears throughout the type system. Every adapter, every seed, every piece of content supports `en` and `ar` natively.

This is not internationalization bolted on after the fact. It is a first-class design decision.

## Who Benefits

- **Agencies** building storefronts for multiple clients on different platforms — write the frontend once, swap adapters per client.
- **Product teams** evaluating platforms — build against the unified types, switch backends without rewriting.
- **Indie developers** who want a commerce backend without platform overhead — use `@commercejs/platform` and own everything.
- **Enterprise teams** adding a new payment provider — implement the `PaymentProvider` interface, no checkout rewrite.

## What We Are Not

Commerce.js is not a hosted platform. It does not manage your inventory, process your taxes, or ship your products. It is a **developer toolkit** — a set of well-tested TypeScript packages that make your commerce code portable, testable, and vendor-independent.

The hard work of commerce — pricing rules, inventory management, fulfillment — stays with your platform of choice. Commerce.js gives you a clean abstraction over the storefront interactions.
